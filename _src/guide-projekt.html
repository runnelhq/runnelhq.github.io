Handbuch

Projekt und Konfiguration

Was sich zwischen Test und Produktion unterscheidet – Pfade, Server, Zugangsdaten – steht nicht in den Workflows, sondern in Environments, Variablen, Secrets und Connections.

Projekt (project.yaml)

Runnel findet das Projekt über project.yaml im Ordner der Datei oder einem übergeordneten Ordner – wie Git den Ordner .git.

kind: Project
apiVersion: runnel/v1
name: flows
description: Datenflüsse der Buchhaltung
defaultEnvironment: dev
variables:
  BASE: D:\data
  INBOX: ${BASE}\inbox
  ARCHIVE: ${BASE}\archive
settings:
  maxConcurrentRuns: 4
  defaultJoin: all
  history:
    keepDays: 90
    cli: errors
FeldBedeutung
name, descriptionName und Zweck des Projekts; erscheinen im Editor
defaultEnvironmentEnvironment, wenn ein Lauf keines nennt, z. B. dev
variablesVariablen für alle Environments; Werte dürfen andere Variablen enthalten
secretStore, secretsWoher ${secret:…} liest, falls ein Environment nichts festlegt – siehe Secrets
settings.maxConcurrentRunshöchstens so viele Läufe des Projekts gleichzeitig auf dem Server; 0 = keine Grenze
settings.history.keepDays, maxRunswie lange beendete Läufe in der Run-Historie bleiben: Standard 30 Tage und höchstens 10.000 Läufe
settings.history.cliwelche Läufe von runnel run bleiben: all (Standard), errors oder none
settings.defaultJoinStandard für Actions mit mehreren eingehenden Links: all, first oder each – siehe Join

Environments

Im Editor öffnen project.yaml und Environments als Formular mit einer Tabelle der Variablen; daneben steht jeweils der Wert aus project.yaml.

Ein Environment überschreibt Variablen für eine Umgebung. Der Name muss dem Dateinamen entsprechen. Gewählt wird es mit --environment, im Editor beim Start oder im Trigger; sonst gilt defaultEnvironment.

kind: Environment
apiVersion: runnel/v1
name: prod
description: Produktivserver
variables:
  BASE: \\fileserver\data
secretStore: env

Variablen

SchreibweiseBedeutung
${NAME}Variable aus Projekt, Environment oder Parametern
${env:NAME}Umgebungsvariable des Betriebssystems, z. B. ${env:COMPUTERNAME}, ${env:TEMP}
${NAME:-text}, ${env:NAME:-text}Standardwert: text, wenn die Variable fehlt oder leer ist, z. B. ${env:TEMP:-C:\Temp}; wörtlicher Text ohne } und ohne weitere ${…}. Secrets haben keinen Standardwert
${secret:NAME}Secret – nur in bestimmten Feldern, siehe unten
${PROJECT_DIR}eingebaut: absoluter Pfad des Projektordners
$${ein wörtliches ${

Gibt es denselben Namen auf mehreren Ebenen, gewinnt die spätere:

  1. Eingebaut: PROJECT_DIR
  2. Standardwerte der Parameter (parameters[].default)
  3. Projekt (project.yaml, variables)
  4. Environment (environments/<name>.yaml)
  5. Beim Start übergebene Parameter: --param, Editor, Trigger, HTTP-Anfrage oder aufrufende Action

Werte dürfen selbst Variablen enthalten (INBOX: ${BASE}\inbox); Zyklen sind ein Fehler. runnel validate warnt je Environment vor nicht definierten Variablen – so fällt auf, wenn eine Variable nur in dev gesetzt ist.

Relative Pfade

Relative Pfade in Actions, Transforms und Triggern beziehen sich immer auf den Projektordner – ohne Projekt auf den Ordner der Datei –, nie auf das Arbeitsverzeichnis. So verhält sich ein Workflow aus der Aufgabenplanung, dem Dienst und dem Editor gleich.

Parameter

Parameter sind die Eingaben eines Workflows oder einer Pipeline. Sie haben einen Typ und optional erlaubte Werte; Standardwerte und übergebene Werte werden geprüft.

parameters:
  - name: DAYS
    description: Wie viele Tage zurück
    type: int
    default: "1"
  - name: MODE
    enum: [full, delta]
    default: delta
  - name: CUSTOMER
    required: true
FeldBedeutung
nameBuchstaben, Ziffern und _, nicht mit einer Ziffer beginnend
typestring (Standard), int, decimal, float, bool, date, datetime, json – dieselben Typen wie bei Feldern in Pipelines
enumerlaubte Werte
defaultStandardwert, auch als Ausdruck, z. B. "{{ formatDate(today(), 'yyyy-MM-dd') }}"
requiredmuss beim Start übergeben werden
descriptionBeschreibung, z. B. für den Startdialog im Editor

Als Variable ${DAYS} ist der Wert immer Text; in Ausdrücken liefert params.DAYS ihn mit seinem Typ.

Secrets

Passwörter und Tokens stehen nie direkt im Workflow, sondern als ${secret:NAME} oder ${secret:QUELLE/NAME}. Erlaubt ist das nur in Feldern für Secrets (z. B. password, token oder headers einer Connection) und als Token von HTTP-Triggern – nicht über eine Variable. Ein fehlendes Secret verhindert den Start; Werte werden in Log, Fehlern und Ergebnissen maskiert.

QuelleWoher der Wert kommt
envaus einer Umgebungsvariablen des Rechners bzw. Dienstkontos – für den Betrieb
inlineim Klartext unter secrets: im Environment oder in project.yaml – nur für Entwicklung und einfache APIs; validate warnt
locallokaler, verschlüsselter Store je Projekt außerhalb des Projektordners, gepflegt mit runnel secret – Standard, wenn kein secretStore gesetzt ist

Die Standardquelle legt secretStore: im Environment fest, sonst in project.yaml. So schreibt der Workflow überall ${secret:ERP_PASSWORD}, und nur das Environment entscheidet, woher der Wert kommt:

kind: Environment
apiVersion: runnel/v1
name: dev
secretStore: inline
secrets:
  ERP_PASSWORD: entwicklung123
kind: Environment
apiVersion: runnel/v1
name: prod
secretStore: env          # liest die Umgebungsvariable ERP_PASSWORD

Lokaler Secret-Store

Ohne secretStore liest ${secret:NAME} aus dem lokalen Store; ${secret:local/NAME} nennt ihn ausdrücklich. Die Werte liegen nie im Projekt, sondern verschlüsselt (AES-256-GCM, an Projekt und Namen gebunden) beim Benutzer in %LOCALAPPDATA%\runnel\secrets. Unter Windows schützt DPAPI den Schlüssel, ohne weiteres Zutun; auf anderen Systemen braucht der Store RUNNEL_MASTER_KEY (32 Zufallsbytes in Base64, z. B. aus openssl rand -base64 32).

runnel secret set ERP_PASSWORD D:\flows        # fragt den Wert verdeckt ab
runnel secret set SFTP_KEY D:\flows --from-file id_ed25519
runnel secret list D:\flows                    # nur Namen, nie Werte
runnel secret missing D:\flows                 # was das Projekt nutzt, aber fehlt
runnel secret delete ERP_PASSWORD D:\flows
  • runnel secret missing zeigt je Environment Quelle, Stand und Fundstelle und endet mit Exit-Code 1, wenn etwas fehlt – passend als Prüfung vor dem Start.
  • Windows-Dienst: Er hat einen eigenen Store in %ProgramData%\runnel\secrets (DPAPI des Rechners, nur für Administratoren und SYSTEM); runnel secret set … --service in einer Konsole „als Administrator“. runnel service install gibt dem Dienstkonto Lesezugriff.
  • Ein Secret ist eine Datei, z. B. ein privater Schlüssel: --from-file; Binärdateien wie PFX mit --base64.
  • Im Editor zeigen Secret-Felder je Environment, ob das Secret gesetzt ist; setzen lässt es sich dort noch nicht.

Connections

Eine Connection beschreibt den Zugang zu einer Datenbank, einer HTTP-API oder einem Mailserver einmal für das ganze Projekt. Bausteine nennen sie mit connection: <name>; validate prüft, ob es sie gibt und ob der Typ passt. Unterschiede zwischen Environments kommen über Variablen.

kind: Connection
apiVersion: runnel/v1
name: erp                       # = Dateiname
description: ERP-Datenbank, nur lesen
type: sqlserver
with:
  host: ${ERP_HOST}
  database: ERP
  user: runnel_read
  password: ${secret:ERP_PASSWORD}

Alle Felder jedes Typs – auch sftp, ftps und ftp für die Actions transfer.* – stehen in der Referenz unter Connection-Typen.

Weitere Typen bringen Plugins mit, z. B. ldap für Active Directory; sie werden geprüft und im Editor bearbeitet wie die eingebauten.

Im Editor öffnen Connections als Formular mit den Feldern ihres Typs (umschaltbar auf YAML). „Test connection“ prüft eine Connection für das gewählte Environment; Secret-Felder zeigen je Environment, ob das Secret gesetzt ist. Neue Connections legt „New → Connection“ an.

SQLite (sqlite)

path PflichtDatenbankdatei, relativ zum Projektordner; wird mit Ordner angelegt, wenn sie fehlt
readOnlynur lesend öffnen (Standard false)

SQL Server (sqlserver)

port / instanceTCP-Port (Standard 1433) oder benannte Instanz wie SQLEXPRESS (braucht den SQL Server Browser)
user, passwordSQL-Server-Anmeldung; ohne user das Windows-Konto, unter dem Runnel läuft (nur Windows)

trustServerCertificatejedes Zertifikat akzeptieren, z. B. selbst signiert; validate warnt
timeoutlängste Zeit für den Verbindungsaufbau, Standard 30s

PostgreSQL (postgres)

host, database, user PflichtServer, Datenbank und Benutzer
portStandard 5432
passwordals ${secret:NAME}
sslModeverify-full (Standard), verify-ca, require oder disable
timeoutStandard 30s

HTTP-API (http)

baseUrl PflichtBasisadresse; die url von http.request ist relativ dazu
headersHeader jeder Anfrage; Werte dürfen ${secret:NAME} enthalten
authnone (Standard), bearer (token), basic (user, password), apiKey (apiKey, apiKeyName, apiKeyIn: header oder query) oder oauth2 (tokenUrl, clientId, clientSecret, scope)

Die Anmeldung geht nur an den Host der baseUrl; mit Anmeldung ist http:// nur zum eigenen Rechner erlaubt. Beispiele für bekannte APIs stehen im Kochbuch.

Mailserver (smtp)

host PflichtMailserver
port, tlsstarttls (Standard, Port 587), tls (Port 465) oder none (nur für ein Relay im vertrauenswürdigen Netz); das Zertifikat wird immer geprüft
authbasic (user, password), oauth2 (Microsoft Entra: tenant, clientId, clientSecret; z. B. Office 365) oder none

SQL bekommt Werte nur als Parameter (@name mit dem Feld params), nie als Text im SQL – das schützt vor SQL-Injection. Beispiel: db.execute.

User guide

Project and configuration

What differs between test and production – paths, servers, credentials – does not live in the workflows but in environments, variables, secrets and connections.

Project (project.yaml)

Runnel finds the project via project.yaml in the file's folder or a parent folder – like Git finds .git.

kind: Project
apiVersion: runnel/v1
name: flows
description: Accounting data flows
defaultEnvironment: dev
variables:
  BASE: D:\data
  INBOX: ${BASE}\inbox
  ARCHIVE: ${BASE}\archive
settings:
  maxConcurrentRuns: 4
  defaultJoin: all
  history:
    keepDays: 90
    cli: errors
FieldMeaning
name, descriptionName and purpose of the project; shown in the editor
defaultEnvironmentEnvironment used when a run names none, e.g. dev
variablesVariables for all environments; values may contain other variables
secretStore, secretsWhere ${secret:…} reads from unless an environment sets its own – see Secrets
settings.maxConcurrentRunsAt most this many runs of the project at once on the server; 0 = no limit
settings.history.keepDays, maxRunsHow long finished runs stay in the run history: default 30 days and at most 10,000 runs
settings.history.cliWhich runs of runnel run are kept: all (default), errors or none
settings.defaultJoinDefault for actions with several incoming links: all, first or each – see Join

Environments

In the editor, project.yaml and environments open as a form with a table of variables, each next to its value from project.yaml.

An environment overrides variables for one environment. Its name must match the file name. It is chosen with --environment, in the editor when starting or in the trigger; otherwise defaultEnvironment applies.

kind: Environment
apiVersion: runnel/v1
name: prod
description: Production server
variables:
  BASE: \\fileserver\data
secretStore: env

Variables

SyntaxMeaning
${NAME}Variable from project, environment or parameters
${env:NAME}Operating system environment variable, e.g. ${env:COMPUTERNAME}, ${env:TEMP}
${NAME:-text}, ${env:NAME:-text}Default: text if the variable is missing or empty, e.g. ${env:TEMP:-C:\Temp}; literal text without } and without further ${…}. Secrets have no default
${secret:NAME}Secret – only in certain fields, see below
${PROJECT_DIR}Built in: absolute path of the project folder
$${A literal ${

If the same name exists on several levels, the later one wins:

  1. Built in: PROJECT_DIR
  2. Parameter defaults (parameters[].default)
  3. Project (project.yaml, variables)
  4. Environment (environments/<name>.yaml)
  5. Parameters passed at start: --param, editor, trigger, HTTP request or calling action

Values may contain variables themselves (INBOX: ${BASE}\inbox); cycles are an error. runnel validate warns about undefined variables per environment – so it shows when a variable is only set in dev.

Relative paths

Relative paths in actions, transforms and triggers always refer to the project folder – without a project to the file's folder – never to the working directory. A workflow behaves the same from Task Scheduler, the service and the editor.

Parameters

Parameters are the inputs of a workflow or pipeline. They have a type and optionally allowed values; defaults and passed values are checked.

parameters:
  - name: DAYS
    description: How many days back
    type: int
    default: "1"
  - name: MODE
    enum: [full, delta]
    default: delta
  - name: CUSTOMER
    required: true
FieldMeaning
nameLetters, digits and _, not starting with a digit
typestring (default), int, decimal, float, bool, date, datetime, json – the same types as for fields in pipelines
enumAllowed values
defaultDefault value, also as an expression, e.g. "{{ formatDate(today(), 'yyyy-MM-dd') }}"
requiredMust be passed at start
descriptionDescription, e.g. for the start dialog in the editor

As a variable ${DAYS} the value is always text; in expressions params.DAYS returns it with its type.

Secrets

Passwords and tokens never go directly into a workflow but appear as ${secret:NAME} or ${secret:SOURCE/NAME}. This is allowed only in secret fields (e.g. a connection's password, token or headers) and as the token of HTTP triggers – not via a variable. A missing secret prevents the start; values are masked in log, errors and results.

SourceWhere the value comes from
envAn environment variable of the machine or service account – for operation
inlinePlain text under secrets: in the environment or project.yaml – only for development and simple APIs; validate warns
localLocal encrypted store per project outside the project folder, maintained with runnel secret – the default if no secretStore is set

The default source is set by secretStore: in the environment, otherwise in project.yaml. The workflow always writes ${secret:ERP_PASSWORD}, and only the environment decides where the value comes from:

kind: Environment
apiVersion: runnel/v1
name: dev
secretStore: inline
secrets:
  ERP_PASSWORD: development123
kind: Environment
apiVersion: runnel/v1
name: prod
secretStore: env          # reads the environment variable ERP_PASSWORD

Local secret store

Without secretStore, ${secret:NAME} reads from the local store; ${secret:local/NAME} names it explicitly. The values never lie in the project but encrypted (AES-256-GCM, bound to project and name) with the user in %LOCALAPPDATA%\runnel\secrets. On Windows, DPAPI protects the key without further setup; on other systems the store needs RUNNEL_MASTER_KEY (32 random bytes in base64, e.g. from openssl rand -base64 32).

runnel secret set ERP_PASSWORD D:\flows        # asks for the value without echo
runnel secret set SFTP_KEY D:\flows --from-file id_ed25519
runnel secret list D:\flows                    # names only, never values
runnel secret missing D:\flows                 # what the project uses but is missing
runnel secret delete ERP_PASSWORD D:\flows
  • runnel secret missing shows source, state and location per environment and exits with code 1 if something is missing – a good check before starting.
  • Windows service: it has its own store in %ProgramData%\runnel\secrets (machine DPAPI, administrators and SYSTEM only); runnel secret set … --service in a console “as administrator”. runnel service install gives the service account read access.
  • A secret that is a file, e.g. a private key: --from-file; binary files such as PFX with --base64.
  • In the editor, secret fields show per environment whether the secret is set; it cannot be set there yet.

Connections

A connection describes access to a database, an HTTP API or a mail server once for the whole project. Components name it with connection: <name>; validate checks that it exists and the type fits. Differences between environments come from variables.

kind: Connection
apiVersion: runnel/v1
name: erp                       # = file name
description: ERP database, read only
type: sqlserver
with:
  host: ${ERP_HOST}
  database: ERP
  user: runnel_read
  password: ${secret:ERP_PASSWORD}

All fields of every type – including sftp, ftps and ftp for the transfer.* actions – are listed in the reference under Connection types.

More types come with plugins, e.g. ldap for Active Directory; they are checked and edited in the editor like the built-in ones.

In the editor connections open as a form with the fields of their type (switchable to YAML). “Test connection” checks a connection for the selected environment; secret fields show per environment whether the secret is set. “New → Connection” creates new ones.

The sign-in only goes to the host of baseUrl; with a sign-in, http:// is only allowed to the local machine. Examples for well-known APIs are in the cookbook.

Mail server (smtp)

host requiredMail server
