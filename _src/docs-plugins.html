Plugins entwickeln

Ein Plugin erweitert Runnel um Actions, Transforms und Connection-Typen, ohne Runnel selbst zu ändern. Es ist ein eigenes Programm in beliebiger Sprache, das Runnel als Kindprozess startet und über JSON-RPC auf stdin/stdout anspricht.

Quelle: docs/dev/PLUGINS.md (verbindliche Beschreibung des Protokolls) · README von sdk-go · Grundlagen: ADR 0019 (Protokoll), ADR 0013 (Namen, Nachtrag 2026-11-24). Stand: Runnel main vom 25.11.2026, sdk-go v0.2.0.

Plugin oder eingebauter Baustein?

Ein Plugin passt, wenn ein Baustein ein fremdes System anbindet, das nicht zum Kern gehört (Verzeichnis, ERP, Fachverfahren), eine Bibliothek mit eigener Laufzeit braucht (.NET-Treiber, SAP NW RFC SDK) oder in einer anderen Sprache geschrieben ist. Allgemeine Bausteine gehören in den Kern – siehe Actions entwickeln.

1. Ein Plugin in Go

Mit dem Go-SDK (Modul github.com/runnelhq/sdk-go, Paket runnel) beschreibt ein Plugin seine Bausteine als Go-Structs; das SDK übernimmt Protokoll, Schema, Parallelität, Abbruch und Log. Es hat keine Abhängigkeiten außer der Standardbibliothek und steht unter MIT.

{{snippet:plugin-hello.go|main.go}} 
kind: Plugin
apiVersion: runnel/v1
name: hello                 # wie der Ordner
version: 1.0.0              # SemVer, wie im Programm
description: Greets
namespace: hello            # Typen des Plugins: hello.greet, …
executable:                 # Text oder je Betriebssystem
  windows: bin/hello.exe
  linux: bin/hello
go build -o D:/flows/plugins/hello/bin/hello.exe .   # GOOS=windows für Windows
runnel plugins trust D:/flows --plugin hello
runnel plugins D:/flows
runnel run D:/flows/workflows/greet.workflow.yaml

Im Workflow steht das Ergebnis unter results.<id>.output; die Zeile von call.Log.Info erscheint im Log des Laufs als [greet] hello: greeting World. Direkt gestartet (ohne RUNNEL_PLUGIN=1) gibt das Programm einen Hinweis aus und endet mit Exit-Code 2.

Konfiguration als Struct

Das JSON Schema der Konfiguration entsteht aus den Tags – genau wie bei den eingebauten Bausteinen (ADR 0014). Runnel prüft with: dagegen, löst Variablen, Ausdrücke und Connections auf und ruft erst dann das Plugin.

TagBedeutung
json:"name"Name des Feldes in der Datei
doc:"…"Beschreibung für Editor und Werkzeuge (englisch, ein Satz)
schema:"required", default=…, example=…, enum=a|bPflichtfeld, Vorgabe, Beispiel, erlaubte Werte
schema:"format=runnel-secret"Passwort oder Token; nur solche Felder dürfen ${secret:…} nutzen
format=runnel-duration, runnel-text, runnel-field, runnel-targetZeitspanne, mehrzeiliger Text, Feld des Eingangs, Ziel-Transform
schema:"group=Advanced", only=mode:bAbschnitt im Formular; Feld gilt nur bei einem Wert eines anderen Feldes
schema:"connection=ldap"Name einer Connection dieses Typs; ein Struct-Feld bekommt die aufgelöste Connection

Texte in Feldern vom Typ Zahl oder bool wandelt das SDK um (ein Wert aus ${N} kommt als Text). Category ist optional: Ohne steht der Baustein in der Palette in einer Gruppe „Plugin: <name>“; mit runnel.CategoryGeneral usw. in der Gruppe der eingebauten. Eine Eingabe braucht runnel.CategoryInput.

Transforms

Ein Transform liest Batches mit Next und schreibt Records mit Emit; das SDK hält die Kredite in beide Richtungen ein. Derselbe Typname darf zugleich Action sein. Aus examples/hello:

{{snippet:plugin-transform.go|Transform hello.greet}}
  • Ziele von Emit: runnel.ToMain (alle Daten-Links ohne eigenes Ziel), runnel.ToError (Fehler-Link mit _error und _errorField) oder die ID eines Transforms aus einem Feld mit format=runnel-target.
  • Werte: int als int64, decimal als Text (exakt), date als "2026-11-24", datetime als time.Time, binary als []byte, null als nil.
  • Init (optional) prüft die Konfiguration und nennt die Felder des Ausgangs – so kennen runnel validate und der Editor die Felder hinter dem Transform. DetectFields (optional) liest für „Detect fields“ die ersten Records einer Eingabe.
  • RecordErrors: true erlaubt einen Fehler-Link, Parallel: true erlaubt copies. Ein error oder panic aus Run beendet den Strom mit Meldung.

Connection-Typen

runnel.AddConnectionType bietet einen eigenen Typ an, z. B. ldap. Der Name ist der Namensraum oder beginnt mit <namensraum>-. Mit Test bietet der Editor „Test connection“ an; dabei soll nichts geschrieben oder gesendet werden außer der Anmeldung. Secrets kommen im Klartext an; Runnel maskiert sie in allem, was zurückkommt – trotzdem nicht loggen.

Testen

  • runneltest.Start(t, newPlugin()) spricht das Protokoll wie Runnel, ohne Prozess: c.Execute(…), c.RunTransform(…), c.Init(…), c.DetectFields(…).
  • runneltest.NewProject baut das Plugin in ein temporäres Projekt, gibt es frei und startet Workflows mit runnel run – wenn RUNNEL_BIN auf Runnel zeigt (make runnel-test RUNNEL_BIN=../runnel/bin/runnel).
  • Von Hand: das Programm mit RUNNEL_PLUGIN=1 starten und die Zeilen des Protokolls eintippen.

2. Ablage und Freigabe

Feld in plugin.yamlRegel
namewie der Ordner unter plugins/; Kleinbuchstaben, Ziffern und -, beginnt mit einem Buchstaben
versionSemVer; passt zum Tag des Repositorys und zur Antwort auf initialize
namespacenicht einer der eingebauten (core, file, http …) und nicht mcp-…; eindeutig im Projekt
executablePfad im Plugin-Ordner (ohne ..), absoluter Pfad oder Befehl des Rechners (z. B. python mit args: [main.py]); je Betriebssystem (windows, linux, darwin). Fehlt das laufende System, wird das Plugin nicht geladen
argsArgumente; Dateien im Plugin-Ordner relativ zu ihm

runnel schema plugin gibt das JSON Schema der Datei aus. Runnel startet ein Plugin erst nach runnel plugins trust: Die Freigabe gilt dem SHA-256 über alle Dateien des Plugin-Ordners (höchstens 1 GB und 10.000 Dateien, keine Verknüpfungen); jede Änderung hebt sie auf. Für Anwender beschrieben im Handbuch.

3. Protokoll

JSON-RPC 2.0, eine Nachricht je Zeile (UTF-8, \n, ein \r davor ist erlaubt), höchstens 16 MiB je Nachricht. stdin: Host → Plugin; stdout: Plugin → Host, nur Protokoll; stderr: Log des Plugins, je Zeile ein Eintrag (DEBUG, INFO, WARN, ERROR am Anfang setzen die Stufe). Das Plugin läuft im Projektordner mit der Umgebung von Runnel und RUNNEL_PLUGIN=1.

{{snippet:plugin-protocol.txt|Ablauf einer Action}}
MethodeAntwort und Regeln
initializeprotocolVersion (1), encoding (json), name wie in plugin.yaml, version, optional concurrency; Zeitgrenze 10 s
describeactions, optional transforms und connectionTypes: Descriptoren wie die eingebauten (type, label, description, schema, optional category, example); nur im eigenen Namensraum; Zeitgrenze 10 s
action.execute{"output": …}, im Workflow result.output; ein Fehler ist eine Fehlerantwort, ihre message die Meldung der Action
connection.test{"ok": true, "message": "…", "version": "…"}; nur für Typen mit "test": true, höchstens 15 s
transform.init, transform.detectFieldsSchema des Ausgangs und Probleme der Konfiguration; erste Records einer Eingabe – je Transform in describe angekündigt
shutdownnull; danach schließt der Host stdin und beendet den Prozess nach 5 s mit allen Kindprozessen
  • Parallelität: ohne concurrency eine Anfrage nach der anderen; mit concurrency: n bis zu n gleichzeitig, Antworten in beliebiger Reihenfolge über id.
  • Abbruch: $/cancelRequest ({"id": n}) bei Abbruch oder Timeout; das Plugin beendet die Arbeit und kann mit -32800 antworten.
  • Unbekannte Methoden beantwortet das Plugin mit -32601; unbekannte Felder ignorieren beide Seiten – Änderungen in Version 1 sind nur additiv.
  • Prozess: einer je Plugin und Lauf, beim ersten Aufruf gestartet, unter Windows in einem Job Object. Endet das Plugin während einer Anfrage oder schreibt es anderes als JSON-RPC auf stdout, scheitert die Anfrage mit den letzten Zeilen von stderr.

Transforms als Strom

{{snippet:plugin-stream.txt|Strom eines Transforms}}

Nur transform.open ist eine Anfrage mit Antwort, alles andere sind Notifications. Kredite: Der Host schickt höchstens window Batches, bevor das Plugin mit $/ack neue freigibt; das Plugin schickt höchstens emitWindow emit, bevor der Host neue freigibt. So bleibt der Speicher auf beiden Seiten begrenzt, und ein langsamer Transform dahinter bremst das Plugin. Alle Transforms eines Plugins in einer Pipeline teilen einen Prozess; stream ordnet die Nachrichten zu. Durchsatz mit dem SDK: etwa 360.000 Records/s (500.000 Records mit 5 Feldern, 4 Kerne).

4. Veröffentlichen

  • Offizielle Plugins liegen in runnelhq/plugin-<name>, SDKs in runnelhq/sdk-<sprache>. Eigene Plugins: Repository runnel-plugin-<name> in der eigenen Organisation, Namensraum mit Präfix der Firma (z. B. contoso-sap); GitHub-Topic runnel-plugin.
  • Release-Archiv: runnel-plugin-<name>_<version>_<os>_<arch>.zip mit dem fertigen Ordner <name>/ (plugin.yaml, Programme, LICENSE, THIRD_PARTY_NOTICES) und SHA256SUMS. Die offiziellen Plugins legen je Archiv eine SBOM (CycloneDX) bei und belegen die Herkunft mit GitHub-Attestations.
  • Versionen: SemVer-Tags, unabhängig von Runnel; die Version in plugin.yaml passt zum Tag.
  • Vorbilder: plugin-iban (Actions und Transform mit Fehler-Link, Init) und plugin-ldap (Connection-Typ mit Test, Eingabe mit „Detect fields“, Tests gegen einen echten Server). Beide zeigen auch Makefile, Lizenzprüfung und Release-Workflow.

5. Sicherheit

  • Ein Plugin läuft mit den Rechten von Runnel, beim Dienst mit dessen Konto – deshalb die Freigabe je Rechner und Projekt.
  • Kein Port: Das Plugin ist nur über stdin/stdout erreichbar. Die Umgebung enthält keine Tokens der HTTP-Trigger.
  • Secrets aus der config maskiert der Host in stderr, Fehlern und output. Das Plugin selbst loggt sie nicht.
  • Eingaben von außen (Filter, Pfade) maskieren bzw. prüfen – wie filterValues bei plugin-ldap. Grenzen für Größe und Zeit setzen.

Developer docs · Extending

Developing plugins

A plugin adds actions, transforms and connection types to Runnel without changing Runnel itself. It is a program of its own in any language, which Runnel starts as a child process and talks to via JSON-RPC over stdin/stdout.

Source (German): docs/dev/PLUGINS.md (the binding protocol description) · README of sdk-go · Background: ADR 0019 (protocol), ADR 0013 (names, addendum 2026-11-24). As of Runnel main on 2026-11-25, sdk-go v0.2.0.

Plugin or built-in component?

A plugin fits when a component connects a third-party system outside the core (directory, ERP, specialist system), needs a library with its own runtime (.NET driver, SAP NW RFC SDK) or is written in another language. General-purpose components belong in the core – see Developing actions.

1. A plugin in Go

With the Go SDK (module github.com/runnelhq/sdk-go, package runnel) a plugin describes its components as Go structs; the SDK handles protocol, schema, concurrency, cancellation and logging. It has no dependencies besides the standard library and is MIT licensed.

{{snippet:plugin-hello.go|main.go}} 
kind: Plugin
apiVersion: runnel/v1
name: hello                 # like the folder
version: 1.0.0              # SemVer, as in the program
description: Greets
namespace: hello            # the plugin's types: hello.greet, …
executable:                 # text or per operating system
  windows: bin/hello.exe
  linux: bin/hello
go build -o D:/flows/plugins/hello/bin/hello.exe .   # GOOS=windows for Windows
runnel plugins trust D:/flows --plugin hello
runnel plugins D:/flows
runnel run D:/flows/workflows/greet.workflow.yaml

In the workflow the result is under results.<id>.output; the line from call.Log.Info appears in the run log as [greet] hello: greeting World. Started directly (without RUNNEL_PLUGIN=1), the program prints a hint and exits with code 2.

Configuration as a struct

The JSON Schema of the configuration comes from the tags – exactly as for built-in components (ADR 0014). Runnel checks with: against it, resolves variables, expressions and connections, and only then calls the plugin.

TagMeaning
json:"name"Name of the field in the file
doc:"…"Description for editor and tools (English, one sentence)
schema:"required", default=…, example=…, enum=a|bRequired field, default, example, allowed values
schema:"format=runnel-secret"Password or token; only such fields may use ${secret:…}
format=runnel-duration, runnel-text, runnel-field, runnel-targetDuration, multi-line text, field of the input, target transform
schema:"group=Advanced", only=mode:bSection in the form; field applies only for a value of another field
schema:"connection=ldap"Name of a connection of this type; a struct field receives the resolved connection

The SDK converts text in number or bool fields (a value from ${N} arrives as text). Category is optional: without it, the component sits in a palette group “Plugin: <name>”; with runnel.CategoryGeneral etc. in the built-in group. An input needs runnel.CategoryInput.

Transforms

A transform reads batches with Next and writes records with Emit; the SDK keeps the credits in both directions. The same type name may be an action too. From examples/hello:

{{snippet:plugin-transform.go|Transform hello.greet}}
  • Targets of Emit: runnel.ToMain (all data links without a target of their own), runnel.ToError (error link with _error and _errorField) or the ID of a transform from a field with format=runnel-target.
  • Values: int as int64, decimal as text (exact), date as "2026-11-24", datetime as time.Time, binary as []byte, null as nil.
  • Init (optional) checks the configuration and names the output fields – so runnel validate and the editor know the fields behind the transform. DetectFields (optional) reads the first records of an input for “Detect fields”.
  • RecordErrors: true allows an error link, Parallel: true allows copies. An error or panic from Run ends the stream with a message.

Connection types

runnel.AddConnectionType offers a type of its own, e.g. ldap. The name is the namespace or starts with <namespace>-. With Test, the editor offers “Test connection”; nothing should be written or sent besides signing in. Secrets arrive in plain text; Runnel masks them in everything that comes back – still, do not log them.

Testing

  • runneltest.Start(t, newPlugin()) speaks the protocol like Runnel, without a process: c.Execute(…), c.RunTransform(…), c.Init(…), c.DetectFields(…).
  • runneltest.NewProject builds the plugin into a temporary project, trusts it and runs workflows with runnel run – when RUNNEL_BIN points to Runnel (make runnel-test RUNNEL_BIN=../runnel/bin/runnel).
  • By hand: start the program with RUNNEL_PLUGIN=1 and type the protocol lines.

2. Layout and trust

Field in plugin.yamlRule
nameLike the folder under plugins/; lowercase letters, digits and -, starts with a letter
versionSemVer; matches the repository tag and the answer to initialize
namespaceNot a built-in one (core, file, http …) and not mcp-…; unique in the project
executablePath in the plugin folder (no ..), absolute path or a command of the machine (e.g. python with args: [main.py]); per operating system (windows, linux, darwin). Without an entry for the running system the plugin is not loaded
argsArguments; files in the plugin folder relative to it

runnel schema plugin prints the file's JSON Schema. Runnel starts a plugin only after runnel plugins trust: the approval applies to the SHA-256 over all files of the plugin folder (at most 1 GB and 10,000 files, no links); any change voids it. Described for users in the user guide.

3. Protocol

JSON-RPC 2.0, one message per line (UTF-8, \n, a preceding \r is allowed), at most 16 MiB per message. stdin: host → plugin; stdout: plugin → host, protocol only; stderr: the plugin's log, one entry per line (DEBUG, INFO, WARN, ERROR at the start set the level). The plugin runs in the project folder with Runnel's environment and RUNNEL_PLUGIN=1.

{{snippet:plugin-protocol.txt|Flow of an action}}
MethodAnswer and rules
initializeprotocolVersion (1), encoding (json), name as in plugin.yaml, version, optional concurrency; time limit 10 s
describeactions, optional transforms and connectionTypes: descriptors like the built-in ones (type, label, description, schema, optional category, example); own namespace only; time limit 10 s
action.execute{"output": …}, in the workflow result.output; an error is an error response, its message the action's message
connection.test{"ok": true, "message": "…", "version": "…"}; only for types with "test": true, at most 15 s
transform.init, transform.detectFieldsOutput schema and configuration problems; first records of an input – announced per transform in describe
shutdownnull; then the host closes stdin and ends the process with all child processes after 5 s
  • Concurrency: without concurrency one request after another; with concurrency: n up to n at once, answers in any order via id.
  • Cancellation: $/cancelRequest ({"id": n}) on cancel or timeout; the plugin stops the work and may answer with -32800.
  • Unknown methods are answered with -32601; both sides ignore unknown fields – changes in version 1 are additive only.
  • Process: one per plugin and run, started on first use, in a job object on Windows. If the plugin ends during a request or writes anything but JSON-RPC to stdout, the request fails with the last lines of stderr.

Transforms as a stream

{{snippet:plugin-stream.txt|Stream of a transform}}

Only transform.open is a request with an answer; everything else is a notification. Credits: the host sends at most window batches before the plugin releases new ones with $/ack; the plugin sends at most emitWindow emit messages before the host releases new ones. That keeps memory bounded on both sides, and a slow transform downstream slows the plugin. All transforms of a plugin in a pipeline share one process; stream routes the messages. Throughput with the SDK: about 360,000 records/s (500,000 records with 5 fields, 4 cores).

4. Publishing

  • Official plugins live in runnelhq/plugin-<name>, SDKs in runnelhq/sdk-<language>. Your own plugins: repository runnel-plugin-<name> in your organization, namespace with a company prefix (e.g. contoso-sap); GitHub topic runnel-plugin.
  • Release archive: runnel-plugin-<name>_<version>_<os>_<arch>.zip with the finished folder <name>/ (plugin.yaml, programs, LICENSE, THIRD_PARTY_NOTICES) and SHA256SUMS. The official plugins add an SBOM (CycloneDX) per archive and prove their origin with GitHub attestations.
  • Versions: SemVer tags, independent of Runnel; the version in plugin.yaml matches the tag.
  • Models: plugin-iban (actions and a transform with error link, Init) and plugin-ldap (connection type with test, input with “Detect fields”, tests against a real server). Both also show Makefile, license check and release workflow.

5. Security

  • A plugin runs with Runnel's rights, in the service with its account – hence the approval per machine and project.
  • No port: the plugin is reachable only via stdin/stdout. Its environment contains no HTTP trigger tokens.
  • The host masks secrets from the config in stderr, errors and output. The plugin itself does not log them.
  • Escape or check outside input (filters, paths) – like filterValues in plugin-ldap. Set limits on size and time.
