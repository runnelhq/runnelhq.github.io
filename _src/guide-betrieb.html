Handbuch

Betrieb

Dieselbe runnel.exe prüft Dateien, führt einmalig aus, startet Editor und Trigger oder läuft dauerhaft als Windows-Dienst.

BefehlZweck
runnel validate <pfad…>Workflows, Pipelines, Trigger und Projektdateien prüfen
runnel run <datei>einen Workflow oder eine Pipeline einmal ausführen
runnel serve [projektordner]Editor im Browser und Trigger starten
runnel triggers [projektordner]Trigger mit Zeitplan und nächstem Zeitpunkt auflisten
runnel service …Windows-Dienst einrichten und steuern
runnel catalog [typ]Bausteine nachschlagen, mit --json als JSON Schema
runnel schema <art>JSON Schema einer Dateiart: project, environment, connection, trigger
runnel versionVersion, Commit und Plattform

Prüfen

runnel validate D:\flows
runnel validate --env prod --strict D:\flows\workflows\import.workflow.yaml

Ordner werden rekursiv durchsucht. Geprüft werden Syntax und Felder, Links und Zyklen, unerreichbare Actions, Variablen gegen jedes Environment (oder nur gegen --env), Ausdrücke, Action- und Transform-Typen mit ihrer Konfiguration sowie Trigger und Connections. Meldungen erscheinen als datei:zeile:spalte: error|warning: text, oft mit Vorschlag („did you mean …?“). Bei Fehlern ist der Exit-Code 1, mit --strict auch bei Warnungen – passend als Schritt in einer CI.

Ausführen

runnel run D:\flows\workflows\import.workflow.yaml
runnel run --env prod --param DAYS=3 --param MODE=full D:\flows\workflows\import.workflow.yaml
runnel run -v D:\flows\pipelines\customers.pipeline.yaml
OptionBedeutung
--env <name>Environment des Projekts; ohne Angabe das defaultEnvironment
--param KEY=VALUEParameter setzen, mehrfach möglich
-vzusätzlich Debug-Meldungen und jeden Start und jedes Ende einer Action bzw. eines Transforms

Pipelines zeigen am Ende je Transform, wie viele Datensätze er gelesen, geschrieben und an Fehler-Links gegeben hat. Strg+C bricht einen Lauf sauber ab; ein zweites Strg+C beendet sofort.

Exit-CodeBedeutung
0erfolgreich
1fehlgeschlagen
2nicht gestartet – ungültiger Workflow, fehlender Parameter oder falscher Aufruf
130abgebrochen (Strg+C)

In der Windows-Aufgabenplanung

Für einfache Zeitpläne ohne laufenden Server genügt die Aufgabenplanung: Programm C:\Tools\Runnel\runnel.exe, Argumente run --env prod D:\flows\workflows\import.workflow.yaml. Die Aufgabe zeigt als Ergebnis den Exit-Code (0 bzw. 0x1 bei Fehler). Alternativ übernehmen Trigger die Zeitpläne, solange der Server oder Dienst läuft.

Editor und Server

runnel serve D:\flows
# Editor: http://127.0.0.1:7300

Der Editor zeigt Workflows und Pipelines als Canvas und als YAML, prüft beim Tippen, startet Läufe und zeigt sie live. Er arbeitet auf denselben Dateien wie die CLI – Änderungen aus Git oder einem Texteditor erkennt er beim Speichern (Konfliktdialog). Solange serve läuft, starten auch die Trigger des Projekts.

OptionBedeutung
--port <n>Port auf 127.0.0.1, Standard 7300; 0 wählt einen freien
--stop-timeout <dauer>Zeit, die laufende Runs beim Beenden bekommen, z. B. 30s
--triggers <adresse>Listener der HTTP-Trigger, Standard 127.0.0.1:7301; "" schaltet ihn ab

Der Editor ist nur vom eigenen Rechner aus erreichbar. Eine Benutzerverwaltung gibt es bewusst nicht; mehrere Browser können gleichzeitig arbeiten.

Windows-Dienst

Für den Dauerbetrieb bedient ein Dienst das Projekt wie runnel serve und führt seine Trigger auch ohne angemeldeten Benutzer aus. Einrichten, Starten, Stoppen und Entfernen brauchen eine Konsole „als Administrator“.

runnel service install D:\flows
runnel service start
runnel service status
runnel service stop
runnel service uninstall
Option von installBedeutung
--name <name>Name des Dienstes, Standard runnel – für mehrere Dienste, z. B. einen je Projekt (dann mit eigenem --port und --triggers)
--account <konto>Standard LocalService (wenige Rechte, Netzfreigaben nur, wenn sie für jeden lesbar sind). Außerdem NetworkService, LocalSystem, ein Benutzerkonto DOMAIN\user (Passwort wird abgefragt, Recht „Als Dienst anmelden“ nötig) oder ein gMSA DOMAIN\name$
--start <art>delayed (Standard: automatisch, kurz nach dem Hochfahren), auto oder manual
--port, --triggerswie bei serve
--stop-timeoutZeit für laufende Runs beim Stoppen, Standard 30 s
  • Rechte: Das Dienstkonto muss den Projektordner lesen und die Ausgabeordner beschreiben können.
  • Wiederherstellung: Nach einem Fehler startet Windows den Dienst nach 10 s, 1 min und 5 min neu.
  • Stoppen: Keine neuen Läufe mehr; laufende bekommen --stop-timeout, danach werden sie abgebrochen.
  • Log: vollständig in %ProgramData%\runnel\logs\<name>.log (mit Rotation), Start, Stopp, Warnungen und Fehler zusätzlich in der Ereignisanzeige.
  • Der Dienst startet die runnel.exe, mit der er eingerichtet wurde. Nach dem Verschieben der exe neu einrichten.

HTTP-Trigger im Netz

HTTP-Trigger lauschen standardmäßig nur lokal. Aus dem Netz erreichbar sind sie nur über HTTPS:

runnel serve --triggers 0.0.0.0:7301 --triggers-tls auto D:\flows
runnel serve --triggers 0.0.0.0:7301 --triggers-cert C:\certs\runnel.crt --triggers-key C:\certs\runnel.key D:\flows
  • --triggers-tls auto erzeugt einmal ein Zertifikat für localhost, den Rechnernamen und seine IP-Adressen und verwendet es wieder; das Log nennt den Fingerabdruck. Aufrufer vertrauen ihm, indem sie triggers.crt importieren (Dienst: %ProgramData%\runnel\tls\, sonst %LOCALAPPDATA%\runnel\tls\).
  • --triggers-cert und --triggers-key nutzen ein eigenes Zertifikat als PEM, z. B. von der Firmen-CA; ein erneuertes wird ohne Neustart übernommen.
  • Reines HTTP im Netz nur mit --triggers-insecure – mit Warnung, denn Tokens und Daten gingen im Klartext.

Details zu Pfaden, Token und Antworten: Trigger – HTTP.

Logs und Läufe

  • CLI: Das Log erscheint in der Konsole; mit -v ausführlich.
  • Editor: Tab „Log“ unter dem Canvas, Status an jeder Action, Ergebnis im Panel.
  • Server und Dienst: Die letzten 100 Läufe (dazu die letzten 100 von HTTP-Triggern) stehen im Speicher und im Editor. Der Dienst schreibt zusätzlich die Log-Datei.
  • Secrets werden in Log, Fehlern und Ergebnissen durch *** ersetzt.

Run-Historie (in Arbeit)

Beschlossen in ADR 0026, umgesetzt in den nächsten Schritten: Läufe überstehen dann Neustarts, und auch Läufe von runnel run und der Aufgabenplanung werden sichtbar. Es bleibt bei „kein Datenbank-Server“ – die Historie ist eine SQLite-Datei, die die exe selbst schreibt; nichts zu installieren und nichts zu verwalten.

  • Ort: eine Datei runs.db je Projekt im Datenordner, nicht im Projektordner (gehört nicht in Git; SQLite ist auf Netzlaufwerken nicht sicher). Dienst: %ProgramData%\runnel\history\…, Benutzer: %LOCALAPPDATA%\runnel\history\…; mit --history-dir frei wählbar, z. B. portabel neben der exe.
  • Inhalt: Lauf, Status je Action bzw. Transform und Log (höchstens 5.000 Zeilen je Lauf); keine Datensätze, Secrets bereits maskiert.
  • Gleichzeitig: Dienst, runnel serve und runnel run schreiben in dieselbe Datei. Ein Fehler der Historie hält keinen Lauf auf.
  • Ansehen: im Editor, über die API oder mit runnel runs bzw. runnel runs <id> – ohne SQLite-Werkzeug.
  • Aufbewahrung in project.yaml unter settings.history: keepDays (Standard 30), maxRuns (10.000), cli (all, errors, none); history: gilt dann für alle Trigger-Arten.

User guide

Operation

The same runnel.exe validates files, runs once, starts the editor and triggers, or runs continuously as a Windows service.

CommandPurpose
runnel validate <path…>Check workflows, pipelines, triggers and project files
runnel run <file>Run a workflow or a pipeline once
runnel serve [project folder]Start the browser-based editor and the triggers
runnel triggers [project folder]List triggers with schedule and next time
runnel service …Set up and control the Windows service
runnel catalog [type]Look up components, with --json as JSON Schema
runnel schema <kind>JSON Schema of a file kind: project, environment, connection, trigger
runnel versionVersion, commit and platform

Validating

runnel validate D:\flows
runnel validate --env prod --strict D:\flows\workflows\import.workflow.yaml

Folders are searched recursively. Checked are syntax and fields, links and cycles, unreachable actions, variables against every environment (or only --env), expressions, action and transform types with their configuration, as well as triggers and connections. Messages appear as file:line:column: error|warning: text, often with a suggestion (“did you mean …?”). On errors the exit code is 1, with --strict also on warnings – suitable as a CI step.

Running

runnel run D:\flows\workflows\import.workflow.yaml
runnel run --env prod --param DAYS=3 --param MODE=full D:\flows\workflows\import.workflow.yaml
runnel run -v D:\flows\pipelines\customers.pipeline.yaml
OptionMeaning
--env <name>Environment of the project; without it the defaultEnvironment
--param KEY=VALUESet a parameter, repeatable
-vAlso debug messages and every start and end of an action or transform

Pipelines show at the end how many records each transform read, wrote and passed to error links. Ctrl+C cancels a run cleanly; a second Ctrl+C exits immediately.

Exit codeMeaning
0succeeded
1failed
2not started – invalid workflow, missing parameter or wrong call
130cancelled (Ctrl+C)

In Windows Task Scheduler

For simple schedules without a running server, Task Scheduler is enough: program C:\Tools\Runnel\runnel.exe, arguments run --env prod D:\flows\workflows\import.workflow.yaml. The task shows the exit code as its result (0, or 0x1 on failure). Alternatively, triggers handle schedules while the server or service is running.

Editor and server

runnel serve D:\flows
# editor: http://127.0.0.1:7300

The editor shows workflows and pipelines as a canvas and as YAML, checks while you type, starts runs and shows them live. It works on the same files as the CLI – changes from Git or a text editor are detected when saving (conflict dialog). While serve runs, the project's triggers start too.

OptionMeaning
--port <n>Port on 127.0.0.1, default 7300; 0 picks a free one
--stop-timeout <duration>Time running runs get when stopping, e.g. 30s
--triggers <address>Listener of HTTP triggers, default 127.0.0.1:7301; "" turns it off

The editor is reachable from the same machine only. There is deliberately no user management; several browsers can work at the same time.

Windows service

For continuous operation, a service serves the project like runnel serve and runs its triggers even without a logged-on user. Installing, starting, stopping and removing require a console “as administrator”.

runnel service install D:\flows
runnel service start
runnel service status
runnel service stop
runnel service uninstall
Option of installMeaning
--name <name>Name of the service, default runnel – for several services, e.g. one per project (each with its own --port and --triggers)
--account <account>Default LocalService (few rights, network shares only if readable by everyone). Also NetworkService, LocalSystem, a user account DOMAIN\user (password is prompted, needs “Log on as a service”) or a gMSA DOMAIN\name$
--start <type>delayed (default: automatic, shortly after boot), auto or manual
--port, --triggersas for serve
--stop-timeoutTime for running runs when stopping, default 30 s
  • Permissions: the service account must be able to read the project folder and write to output folders.
  • Recovery: after a failure, Windows restarts the service after 10 s, 1 min and 5 min.
  • Stopping: no new runs; running ones get --stop-timeout, then they are cancelled.
  • Log: in full in %ProgramData%\runnel\logs\<name>.log (rotated); start, stop, warnings and errors also in the Event Log.
  • The service starts the runnel.exe it was set up with. After moving the executable, set it up again.

HTTP triggers on the network

HTTP triggers listen locally by default. They are reachable from the network over HTTPS only:

runnel serve --triggers 0.0.0.0:7301 --triggers-tls auto D:\flows
runnel serve --triggers 0.0.0.0:7301 --triggers-cert C:\certs\runnel.crt --triggers-key C:\certs\runnel.key D:\flows
  • --triggers-tls auto creates a certificate once for localhost, the machine name and its IP addresses and reuses it; the log shows its fingerprint. Callers trust it by importing triggers.crt (service: %ProgramData%\runnel\tls\, otherwise %LOCALAPPDATA%\runnel\tls\).
  • --triggers-cert and --triggers-key use your own PEM certificate, e.g. from the company CA; a renewed one is picked up without restart.
  • Plain HTTP on the network only with --triggers-insecure – with a warning, since tokens and data would travel in plain text.

Details on paths, tokens and responses: Triggers – HTTP.

Logs and runs

  • CLI: the log appears in the console; detailed with -v.
  • Editor: “Log” tab below the canvas, status on every action, result in the panel.
  • Server and service: the last 100 runs (plus the last 100 from HTTP triggers) are kept in memory and shown in the editor. The service also writes the log file.
  • Secrets are replaced by *** in log, errors and results.

Run history (in progress)

Decided in ADR 0026 (German), implemented in the next steps: runs then survive restarts, and runs from runnel run and the Task Scheduler become visible too. It stays “no database server” – the history is an SQLite file handled by the executable itself, nothing to install or administer.

  • Location: one file runs.db per project in the data folder, not in the project folder (it does not belong in Git; SQLite is not safe on network drives). Service: %ProgramData%\runnel\history\…, user: %LOCALAPPDATA%\runnel\history\…; --history-dir sets it freely, e.g. portable next to the executable.
  • Content: run, status per action or transform and log (at most 5,000 lines per run); no records, secrets already masked.
  • Concurrent: service, runnel serve and runnel run write to the same file. A history error never holds up a run.
  • Viewing: in the editor, via the API or with runnel runs or runnel runs <id> – no SQLite tool needed.
  • Retention in project.yaml under settings.history: keepDays (default 30), maxRuns (10,000), cli (all, errors, none); history: then applies to all trigger kinds.
