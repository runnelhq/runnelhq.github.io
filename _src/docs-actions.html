Eine neue Action entwickeln

Actions sind die Bausteine von Workflows: Sie tun einmal pro Lauf etwas – eine Datei kopieren, einen HTTP-Aufruf senden, warten. Diese Anleitung beschreibt eingebaute Actions im Go-Code von Runnel.

Quelle: docs/dev/ACTIONS.md · Grundlagen: ADR 0013, Konzept Kap. 6.1 und Kap. 12. Die Anleitung wird mit jedem Schritt aktualisiert, der den Vertrag einer Action ändert.

Vertragstest

Ein Teil der Regeln wird automatisch geprüft: internal/actions/actions_test.go testet jede eingebaute Action auf gültigen Typnamen, reservierten Namensraum, Beschreibung, Ablehnung unbekannter Felder und Ende bei abgebrochenem Lauf.

1. Action, Transform oder Plugin?

Wenn …dann
ein Schritt einmal pro Workflow-Lauf etwas tut (Datei kopieren, HTTP-Aufruf, Mail senden)Action
Datensätze in einer Pipeline verarbeitet werden (lesen, umformen, schreiben)Transform – Anleitung folgt mit S12/S13
der Baustein ein fremdes System anbindet, das nicht zum Kern gehört (SAP, Spezial-APIs), oder in einer anderen Sprache geschrieben istPlugin – Anleitung folgt mit S49–S51

Derselbe Name darf als Action und als Transform existieren, zum Beispiel http.request. Welche Registry gilt, ergibt sich aus der Datei: *.workflow.yaml → Actions, *.pipeline.yaml → Transforms. In Doku und Editor wird die Art deshalb immer mitgenannt: „Action http.request“.

2. Namensraum und Typname

  • Typnamen haben die Form <namensraum>.<name>: Kleinbuchstaben, Ziffern und -, z. B. file.copy, http.request.
  • Der Name beschreibt die Tätigkeit (copy, wait, send), nicht die Technik.
  • Eingebaute Actions liegen in einem reservierten Namensraum (internal/model/namespaces.go). Plugins können eingebaute Bausteine daher weder überschreiben noch mit anderen Plugins kollidieren.

Reservierte Namensräume

  • core
  • ai
  • csv
  • db
  • excel
  • file
  • ftp
  • http
  • json
  • mail
  • mcp
  • sftp
  • shell
  • xml
  • zip
  • mcp-<connection>

Hervorgehoben: Namensraum mit bereits umgesetzten Actions. mcp-<connection> steht für Werkzeuge eines als Connection eingebundenen MCP-Servers (ADR 0012).

Neuer Namensraum? Nur wenn kein bestehender passt:

  1. in reservedNamespaces eintragen, falls noch nicht vorhanden,
  2. Paket internal/actions/<namensraum>/ mit register.go anlegen,
  3. dessen Register in internal/actions/actions.go (namespaces) eintragen.

Ein Paket je Namensraum, eine Datei je Action, die Tests direkt daneben:

Die Registrierung hat zwei Ebenen. register.go listet die Actions des Namensraums – eine neue Action ändert also nur ihr eigenes Paket, und die Definitionen bleiben unexportiert. actions.go listet die Namensräume und liefert Builtin() für CLI, Server und MCP; die Engine kennt keine konkreten Actions.

Bewusst nicht gewählt (ADR 0013): eine zentrale Liste aller einzelnen Actions (Merge-Konflikte, exportierte Definitionen), Selbstregistrierung über init() (implizit, schwer zu testen) und ein Paket je Action (zu kleinteilig).

Kopiervorlage ist core.wait samt Test. Mehrere eng verwandte Actions dürfen sich eine Datei teilen, wenn sie dieselbe Implementierung nutzen – Beispiel: core.success und core.abort in end.go.

4. Definition und Konfiguration

{{snippet:copy-definition.go|Beispiel: file.copy}}

Lebenszyklus: New wird zweimal aufgerufen. Deshalb prüft es nur die Struktur – Werte erst in Execute.

  1. PrüfenNew(with)mit dem Text aus der Datei – Werte können noch ${…} enthalten
  2. Auflösen${VAR}Variablen und Parameter werden eingesetzt
  3. ErzeugenNew(with)erneut, mit aufgelösten Werten, vor jeder Ausführung
  4. AusführenExecute(ctx, ec)Ergebnis oder Fehler – entscheidet über Erfolgs- und Fehler-Links

Regeln:

  • Felder der Konfiguration (with:) als Struct mit json-Tags; Feldnamen in camelCase, wie im YAML.
  • DecodeConfig verwenden – es lehnt unbekannte Felder ab, sodass Tippfehler im Workflow gemeldet werden. Der Vertragstest prüft das.
  • New prüft nur die Struktur: Pflichtfelder, Typen, unbekannte Felder. Werte wie Dauern, Zahlen in Textform oder Pfade werden erst in Execute geprüft.
  • Zeitangaben als string übernehmen und in Execute mit model.Duration(s).Value() umwandeln.
  • Actions ohne Konfiguration lehnen jedes Feld ab (len(with) > 0 → Fehler); Vorlage: core/dummy.go.
  • Beschreibung (Description): ein kurzer englischer Satz ohne Punkt; erscheint später in der Palette des Editors.
  • Kommentar über der Definition: was die Action tut, Besonderheiten, neue Konfigurationsfelder – später die Grundlage für das Schema im Editor.

5. Ausführen (Execute)

{{snippet:copy-execute.go|Beispiel: file.copy}}
ThemaRegel
Abbruch und Timeoutctx an alle blockierenden Aufrufe weitergeben (HTTP, DB, Prozesse) bzw. regelmäßig ctx.Err() prüfen; bei Abbruch ctx.Err() zurückgeben. Der Vertragstest prüft, dass eine Action bei abgebrochenem Lauf endet.
FehlerEin zurückgegebener Fehler bedeutet „fehlgeschlagen“ → Fehler-Links, Retry. Meldungen für Anwender formulieren: was, wo, warum – englisch, ohne Stacktrace, z. B. cannot copy "a.csv" to "D:\out": access denied.
Keine PanicsFehler zurückgeben, nie panic; keine globalen Zustände ändern.
Logec.Log / ec.Logf: Info für das Ergebnis (eine Zeile), Debug für Details (sichtbar mit -v), Warn für Auffälliges, das kein Fehler ist.
SecretsPasswörter, Tokens und ${secret:…}-Werte nie loggen und nicht in Fehlermeldungen aufnehmen.
Result.EndNur für Actions, die den Workflow beenden (core.success, core.abort); sonst leeres Result.
Ausgabedatenkommt mit S08 Strukturierte Ergebnisse (z. B. Dateiliste, Statuscode) für nachfolgende Actions über result.output.
WiederholbarkeitEine Action kann wiederholt werden (retry, Schleifen) und sollte bei erneutem Aufruf sinnvoll funktionieren – z. B. Zieldatei überschreiben oder klar melden.
NebenläufigkeitMehrere Instanzen können gleichzeitig laufen (parallele Zweige, join: each); keine gemeinsamen veränderlichen Variablen.

6. Windows-Besonderheiten

Runnel ist Windows-first. Actions, die mit Dateien, Prozessen oder Netzwerk arbeiten, beachten:

  • Pfade: path/filepath statt path; Laufwerke (D:\), UNC-Pfade (\\server\share\…), Leerzeichen, lange Pfade (> 260 Zeichen).
  • Groß-/Kleinschreibung: Dateinamen sind unter Windows nicht case-sensitiv.
  • Gesperrte Dateien: Dateien, die ein anderes Programm geöffnet hat, verständlich melden.
  • Kodierungen: Textdateien können UTF-8 (mit oder ohne BOM), UTF-16 oder Windows-1252 sein.
  • Prozesse: Argumente nicht über eine Shell zusammensetzen (keine Injection); Kindprozesse bei Abbruch beenden.

7. Tests

{{snippet:copy-test.go|Beispiel: file.copy}}

Pflicht:

  • Konfigurationsfehler (fehlende Pflichtfelder, falsche Werte) mit actiontest.ConfigError.
  • Erfolgsfall und die wichtigsten Fehlerfälle von Execute, inklusive Meldungstext.
  • Abbruch für Actions, die länger laufen können (context.WithCancel / WithTimeout).
  • Vertragstest: Braucht die Action Pflichtfelder, eine Beispielkonfiguration in samples von TestContractCancellation (internal/actions/actions_test.go) ergänzen – der Test meldet sich sonst.
  • Nur t.TempDir() und lokale Testserver (httptest) – keine Abhängigkeit von Netz oder Rechnernamen.
  • Tests dürfen nicht die vollständige Liste aller Action-Typen erwarten; sie wächst mit jeder neuen Action.
  • Tests müssen unter Linux und Windows laufen – die CI prüft beides.
Hilfe aus actiontestZweck
New(t, def, with)Erzeugt die Action; ein Konfigurationsfehler lässt den Test fehlschlagen.
ConfigError(t, def, with, want)Erwartet, dass New mit einer Meldung scheitert, die want enthält.
Execute(ctx, a)Führt die Action aus (Run-ID run, Action-ID act) und liefert Ergebnis, Log-Meldungen und Fehler.

8. Dokumentation und Beispiel im selben PR

  • Bausteinliste im Konzept, Kap. 12 bzw. den Roadmap-Schritt als erledigt markieren.
  • Neue Konfigurationsfelder kurz im Kommentar der Definition beschreiben.
  • Bei Bedarf ein Beispiel-Workflow unter examples/, der in internal/cli/validate_test.go mitgeprüft wird. Ein neues Beispiel ändert die Anzahl geprüfter Dateien: Erwartung in TestValidateExamples anpassen, go test ./internal/cli -update ausführen und den Diff der Golden-Datei prüfen.

9. Checkliste für den PR

  • Typname im passenden, reservierten Namensraum; bei neuem Namensraum: namespaces.go, register.go, actions.go
  • Eine Datei je Action, Tests daneben, Eintrag in register.go
  • Konfiguration über DecodeConfig; New prüft nur Struktur, Werte werden in Execute geprüft
  • ctx wird beachtet (Abbruch, Timeout); keine Panics; keine Secrets im Log
  • Verständliche englische Fehlermeldungen
  • Tests: Konfiguration, Erfolg, Fehler, Abbruch; ggf. Beispielkonfiguration im Vertragstest
  • make lint und make test grün
  • Doku und ggf. Beispiel aktualisiert

Developer docs · Components

Developing a new action

Actions are the building blocks of workflows: each does something once per run – copy a file, send an HTTP request, wait. This guide covers built-in actions in Runnel's Go code.

Source (German): docs/dev/ACTIONS.md · Background: ADR 0013, concept ch. 6.1 and ch. 12. The guide is updated with every step that changes the action contract.

Contract test

Some rules are checked automatically: internal/actions/actions_test.go tests every built-in action for a valid type name, a reserved namespace, a description, rejection of unknown fields and termination when the run is cancelled.

1. Action, transform or plugin?

If …then
a step does something once per workflow run (copy a file, HTTP call, send mail)Action
records are processed in a pipeline (read, transform, write)Transform – guide follows with S12/S13
the component connects a third-party system outside the core (SAP, special APIs) or is written in another languagePlugin – guide follows with S49–S51

The same name may exist as an action and as a transform, for example http.request. The file decides which registry applies: *.workflow.yaml → actions, *.pipeline.yaml → transforms. Docs and editor therefore always name the kind: “action http.request”.

2. Namespace and type name

  • Type names have the form <namespace>.<name>: lowercase letters, digits and -, e.g. file.copy, http.request.
  • The name describes the activity (copy, wait, send), not the technology.
  • Built-in actions live in a reserved namespace (internal/model/namespaces.go). Plugins can therefore neither override built-in components nor collide with other plugins.

Reserved namespaces

  • core
  • ai
  • csv
  • db
  • excel
  • file
  • ftp
  • http
  • json
  • mail
  • mcp
  • sftp
  • shell
  • xml
  • zip
  • mcp-<connection>

Highlighted: namespace with actions already implemented. mcp-<connection> stands for the tools of an MCP server added as a connection (ADR 0012).

New namespace? Only if no existing one fits:

  1. add it to reservedNamespaces if it is not there yet,
  2. create the package internal/actions/<namespace>/ with a register.go,
  3. add its Register to internal/actions/actions.go (namespaces).

3. Files and registration

One package per namespace, one file per action, tests right next to it:

{{snippet:files-en.txt|Layout}}

Registration has two levels. register.go lists the actions of the namespace – so a new action only touches its own package and the definitions stay unexported. actions.go lists the namespaces and provides Builtin() for CLI, server and MCP; the engine knows no concrete actions.

{{snippet:register.go|internal/actions/core/register.go}} {{snippet:actions.go|internal/actions/actions.go (excerpt)}}

Deliberately not chosen (ADR 0013): one central list of every single action (merge conflicts, exported definitions), self-registration via init() (implicit, hard to test) and one package per action (too fine-grained).

Use core.wait and its test as a template. Several closely related actions may share a file if they share their implementation – for example core.success and core.abort in end.go.

4. Definition and configuration

{{snippet:copy-definition.go|Example: file.copy}}

Lifecycle: New is called twice. That is why it only checks the structure – values are checked in Execute.

  1. ValidateNew(with)with the text from the file – values may still contain ${…}
  2. Resolve${VAR}variables and parameters are substituted
  3. CreateNew(with)again, with resolved values, before every execution
  4. ExecuteExecute(ctx, ec)result or error – decides between success and failure links

Rules:

  • Configuration fields (with:) as a struct with json tags; field names in camelCase, as in the YAML.
  • Use DecodeConfig – it rejects unknown fields so typos in workflows are reported. The contract test checks this.
  • New only checks the structure: required fields, types, unknown fields. Values such as durations, numbers as text or paths are checked in Execute.
  • Take durations as a string and convert them in Execute with model.Duration(s).Value().
  • Actions without configuration reject every field (len(with) > 0 → error); template: core/dummy.go.
  • Description (Description): a short English sentence without a full stop; later shown in the editor's palette.
  • Comment above the definition: what the action does, special cases, new configuration fields – later the basis for the editor schema.

5. Executing (Execute)

{{snippet:copy-execute.go|Example: file.copy}}
TopicRule
Cancellation and timeoutPass ctx to every blocking call (HTTP, DB, processes) or check ctx.Err() regularly; return ctx.Err() when cancelled. The contract test checks that an action ends when the run is cancelled.
ErrorsA returned error means “failed” → failure links, retry. Write messages for users: what, where, why – in English, no stack trace, e.g. cannot copy "a.csv" to "D:\out": access denied.
No panicsReturn errors, never panic; don't change global state.
Logec.Log / ec.Logf: Info for the result (one line), Debug for details (visible with -v), Warn for anything notable that is not an error.
SecretsNever log passwords, tokens or ${secret:…} values, and keep them out of error messages.
Result.EndOnly for actions that end the workflow (core.success, core.abort); otherwise an empty Result.
Output datacoming with S08 Structured results (e.g. file list, status code) for subsequent actions via result.output.
RepeatabilityAn action can be repeated (retry, loops) and should behave sensibly when called again – e.g. overwrite the target file or report clearly.
ConcurrencySeveral instances can run at once (parallel branches, join: each); no shared mutable variables.

6. Windows specifics

Runnel is Windows first. Actions that work with files, processes or the network take care of:

  • Paths: path/filepath instead of path; drives (D:\), UNC paths (\\server\share\…), spaces, long paths (> 260 characters).
  • Case: file names are not case-sensitive on Windows.
  • Locked files: report files opened by another program in an understandable way.
  • Encodings: text files may be UTF-8 (with or without BOM), UTF-16 or Windows-1252.
  • Processes: don't build arguments through a shell (no injection); end child processes on cancellation.

7. Tests

{{snippet:copy-test-en.go|Example: file.copy}}

Required:

  • Configuration errors (missing required fields, wrong values) with actiontest.ConfigError.
  • The success case and the most important failure cases of Execute, including the message text.
  • Cancellation for actions that can run for a while (context.WithCancel / WithTimeout).
  • Contract test: if the action has required fields, add a sample configuration to samples in TestContractCancellation (internal/actions/actions_test.go) – otherwise the test complains.
  • Only t.TempDir() and local test servers (httptest) – no dependency on the network or machine names.
  • Tests must not expect the complete list of action types; it grows with every new action.
  • Tests must run on Linux and Windows – CI checks both.
Helper from actiontestPurpose
New(t, def, with)Creates the action; a configuration error fails the test.
ConfigError(t, def, with, want)Expects New to fail with a message containing want.
Execute(ctx, a)Runs the action (run ID run, action ID act) and returns the result, log messages and error.

8. Docs and example in the same PR

  • Mark the component list in the concept, ch. 12 or the roadmap step as done.
  • Briefly describe new configuration fields in the comment above the definition.
  • If useful, add an example workflow under examples/; it is checked by internal/cli/validate_test.go. A new example changes the number of checked files: adjust the expectation in TestValidateExamples, run go test ./internal/cli -update and review the golden-file diff.

9. Pull request checklist

  • Type name in the matching reserved namespace; for a new namespace: namespaces.go, register.go, actions.go
  • One file per action, tests next to it, entry in register.go
  • Configuration via DecodeConfig; New only checks structure, values are checked in Execute
  • ctx is respected (cancellation, timeout); no panics; no secrets in the log
  • Understandable English error messages
  • Tests: configuration, success, failure, cancellation; sample configuration in the contract test if needed
  • make lint and make test pass
  • Docs and, if needed, example updated
