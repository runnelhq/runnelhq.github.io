Pipelines

Eine Pipeline bewegt Daten: Alle Transforms laufen gleichzeitig und reichen Datensätze über Links weiter. Der Speicher bleibt dabei konstant, auch bei Millionen Zeilen.

Beispiel

Liest eine CSV-Datei im deutschen Format, wandelt Kundennummer und Umsatz in Zahlen um, behält aktive Kunden, benennt die Felder für ein CRM um und schreibt das Ergebnis. Zeilen mit ungültigen Werten gehen über den Fehler-Link in eine eigene Datei, statt die Pipeline anzuhalten.

{{snippet:guide-customers.pipeline.yaml|pipelines/customers.pipeline.yaml}} 
INFO  [types] read 4, written 3, errors 1 in 0s
INFO  [active] kept 2 of 3 records, dropped 1
INFO  [rejected] wrote 1 row to out/customers-rejected.csv
INFO  [write] wrote 2 rows to out/customers-crm.csv
INFO  pipeline "customers" succeeded in 1ms

Pipelines sind azyklisch: Datensätze fließen nur vorwärts. Hat ein Transform mehrere ausgehende Daten-Links, bekommt bei distribution: copy (Standard) jeder Link jeden Datensatz, bei distribute werden sie reihum verteilt.

Datensätze und Typen

Ein Datensatz ist eine geordnete Liste von Feldern (Name → Wert). Pipelines sind schemalos mit optionalen Typen: Ohne Felddefinition liest z. B. csv.input alles als Text; core.convert oder die fields eines Eingabe-Transforms legen Typen fest.

TypInhalt
stringText
int, decimal, floatGanzzahl, exakte Dezimalzahl (für Beträge), Gleitkommazahl
boolWahrheitswert
date, datetimeDatum, Zeitpunkt
jsonverschachtelte Werte (Objekte, Listen)

Formate beschreiben Text: Zahlen wie #.##0,00 (deutsch) oder #,##0.00, Daten wie dd.MM.yyyy. Ohne Format gelten 1234.5 und ISO-Daten. Eingabedateien dürfen UTF-8 (mit oder ohne BOM), UTF-16 oder Windows-1252 sein (encoding). Im Editor schlägt „Detect fields…“ Felder und Typen aus einer Beispieldatei vor.

runnel validate prüft, ob die Felder, die ein Transform liest, am Link davor bekannt sind – mit Vorschlag bei Tippfehlern.

Dateiformate

FormatLesenSchreibenBesonderheiten
CSVcsv.inputcsv.outputTrennzeichen, Kopfzeile, Kodierung (UTF-8, UTF-16, Windows-1252); beim Schreiben Standard UTF-8 mit BOM, damit Excel Umlaute erkennt
JSON, NDJSONjson.inputjson.outputrecords wählt eine Liste im Dokument; NDJSON ein Objekt je Zeile
Excel (.xlsx)excel.inputexcel.outputBlatt (sheet), Bereich ab einer Zelle (range: A3), Ende bei leerer Zeile (emptyRows: stop); Zahlen und Daten kommen typisiert. Beim Schreiben bleiben Zahlen und Daten Zahlen und Daten, Excel zeigt sie im Format von fields[].format; ifExists: sheet ersetzt nur ein Blatt
XMLxml.inputxml.outputrecords ist der Pfad der Elemente (Bestellungen/Bestellung); from liest Attribute (@nr) und verschachtelte Elemente (Kunde/Name); Namensräume werden ohne Präfix verglichen

Die Felder heißen bei allen Formaten gleich:

  • fields[].from beim Lesen: Spalte, Schlüssel oder Pfad in der Datei – leer wie name.
  • fields[].as beim Schreiben: Spalte, Schlüssel oder Pfad in der Datei – leer wie name. Dasselbe as benennt Felder in core.select-fields um.
  • fields[].format: immer ein Runnel-Muster wie #.##0,00 oder dd.MM.yyyy; in Excel zusätzlich excelFormat für eigene Excel-Codes.
  • ifExists an Ausgaben: replace (Standard; geschrieben über eine temporäre Datei, bei einem Fehler bleibt die alte), append (CSV) oder fail.

Alte Feldnamen wie rename oder overwrite meldet runnel validate bis Version 1.0 mit dem neuen Namen. Rezepte mit Excel und XML stehen im Kochbuch.

Fehler-Links

Kann ein Transform einen einzelnen Datensatz nicht verarbeiten (z. B. „k. A.“ als Zahl), geht er über einen Link mit type: error weiter – unverändert, ergänzt um _error (Meldung), _errorField (Feld) und _errorTransform (ID). Ohne Fehler-Link bricht die Pipeline ab. Welche Transforms Fehler-Links nutzen, zeigt die Referenz (Kennzeichen „Fehler-Link“); an anderen warnt validate, dass der Link nie genutzt wird.

Info-Links und Joins

Ein Link mit type: info bringt Nachschlagedaten zu einem Transform, der sie annimmt – etwa core.stream-lookup, der jedem Datensatz die Felder des passenden Nachschlage-Datensatzes hinzufügt. Der Transform liest den Info-Link vollständig, bevor er seine Daten-Links liest. Er darf nicht aus demselben Transform stammen wie die Daten-Links, sonst würde die Pipeline blockieren; runnel validate meldet das. core.merge-join verbindet zwei nach denselben Schlüsseln sortierte Eingänge wie ein Join in einer Datenbank.

Parallelität

Alle Transforms laufen ohnehin gleichzeitig. Mit copies: n (1–64) läuft ein Transform zusätzlich in n Instanzen, die sich die eingehenden Datensätze teilen – sinnvoll für teure Schritte je Datensatz. Nicht für Ein- und Ausgaben, und die Reihenfolge der Datensätze ist danach nicht mehr garantiert.

Ausführen und testen

  • Direkt: runnel run pipelines/customers.pipeline.yaml – am Ende stehen die Zähler je Transform.
  • Aus einem Workflow: core.run-pipeline mit params; die Zähler stehen im Ergebnis (output.transforms.<id>.written, output.errors). Datensätze gehen mit rows hinein und über core.to-result zurück.
  • Per Trigger: Trigger starten Pipelines wie Workflows, z. B. eine je neuer Datei.
  • Im Editor: „Preview data“ zeigt die Datensätze bis zu einem Transform als Tabelle oder JSON, ohne zu schreiben.
Ausgabeordner

csv.output und json.output legen fehlende Ordner nicht an. Der Ordner der Ausgabedatei muss existieren – sonst scheitert der Transform mit „no such file or directory“. Bei Bedarf vorher mit file.mkdir anlegen.

User guide

Pipelines

A pipeline moves data: all transforms run at the same time and pass records along links. Memory stays constant, even with millions of rows.

Example

Reads a CSV file in German format, converts customer number and revenue into numbers, keeps active customers, renames the fields for a CRM and writes the result. Rows with invalid values go over the error link into a separate file instead of stopping the pipeline.

{{snippet:guide-customers.pipeline.yaml|pipelines/customers.pipeline.yaml}} 
INFO  [types] read 4, written 3, errors 1 in 0s
INFO  [active] kept 2 of 3 records, dropped 1
INFO  [rejected] wrote 1 row to out/customers-rejected.csv
INFO  [write] wrote 2 rows to out/customers-crm.csv
INFO  pipeline "customers" succeeded in 1ms

File layout

FieldMeaning

description, parametersAs for workflows; pipelines have no outputs

linksfrom, to and type: data (default), error or info

settings.strictEvery link must have a fully known schema; warnings about unknown fields become errors
layoutPositions in the editor

Pipelines are acyclic: records only flow forward. If a transform has several outgoing data links, with distribution: copy (default) every link gets every record; with distribute they are handed out in turn.

Records and types

A record is an ordered list of fields (name → value). Pipelines are schemaless with optional types: without a field definition, csv.input for example reads everything as text; core.convert or the fields of an input transform set types.

TypeContent
stringText
int, decimal, floatInteger, exact decimal (for amounts), floating point
boolBoolean
date, datetimeDate, point in time
jsonNested values (objects, lists)

Formats describe text: numbers like #.##0,00 (German) or #,##0.00, dates like dd.MM.yyyy. Without a format, 1234.5 and ISO dates apply. Input files may be UTF-8 (with or without BOM), UTF-16 or Windows-1252 (encoding). In the editor, “Detect fields…” proposes fields and types from a sample file.

runnel validate checks that the fields a transform reads are known on the link before it – with a suggestion for typos.

File formats

FormatReadWriteNotes
CSVcsv.inputcsv.outputDelimiter, header, encoding (UTF-8, UTF-16, Windows-1252); writing defaults to UTF-8 with BOM so Excel recognizes umlauts
JSON, NDJSONjson.inputjson.outputrecords picks a list inside the document; NDJSON one object per line
Excel (.xlsx)excel.inputexcel.outputSheet (sheet), range from a cell (range: A3), end at an empty row (emptyRows: stop); numbers and dates come typed. When writing, numbers and dates stay numbers and dates and Excel shows them in the format of fields[].format; ifExists: sheet replaces just one sheet
XMLxml.inputxml.outputrecords is the path of the elements (Orders/Order); from reads attributes (@nr) and nested elements (Customer/Name); namespaces are compared without prefix

Fields have the same names in every format:

  • fields[].from when reading: column, key or path in the file – empty like name.
  • fields[].as when writing: column, key or path in the file – empty like name. The same as renames fields in core.select-fields.
  • fields[].format: always a Runnel pattern such as #.##0,00 or dd.MM.yyyy; Excel additionally has excelFormat for custom Excel codes.
  • ifExists on outputs: replace (default; written via a temporary file, the old one stays on error), append (CSV) or fail.

Until version 1.0, runnel validate reports old field names such as rename or overwrite with their new name. Recipes with Excel and XML are in the cookbook.

Error links

If a transform can't process a single record (e.g. “n/a” as a number), it passes it on over a link with type: error – unchanged, extended by _error (message), _errorField (field) and _errorTransform (ID). Without an error link the pipeline stops. Which transforms use error links is shown in the reference (marked “error link”); on others validate warns that the link is never used.

Info links and joins

A link with type: info brings lookup data to a transform that accepts it – such as core.stream-lookup, which adds the fields of the matching lookup record to each record. The transform reads the info link completely before reading its data links. It must not come from the same transform as the data links, or the pipeline would block; runnel validate reports this. core.merge-join joins two inputs sorted by the same keys, like a join in a database.

Parallelism

All transforms run concurrently anyway. With copies: n (1–64) a transform that allows it (marked “copies” in the reference) additionally runs as n instances sharing the incoming records – useful for expensive per-record steps. Not for inputs and outputs, and record order is no longer guaranteed afterwards.

Running and testing

  • Directly: runnel run pipelines/customers.pipeline.yaml – the counts per transform are shown at the end.
  • From a workflow: core.run-pipeline with params; the counts are in the result (output.transforms.<id>.written, output.errors). Records go in with rows and come back via core.to-result.
  • Via a trigger: triggers start pipelines like workflows, e.g. one per new file.
  • In the editor: “Preview data” shows the records up to a transform as a table or JSON, without writing.
Output folders

csv.output and json.output don't create missing folders. The output file's folder must exist – otherwise the transform fails with “no such file or directory”. Create it beforehand with file.mkdir if needed.
