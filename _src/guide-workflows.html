Workflows

Ein Workflow steuert einen Ablauf: Actions laufen entlang von Links, nacheinander oder parallel. Jede Action endet mit Erfolg oder Fehler, und die Links entscheiden, wie es weitergeht.

Beispiel

Wartet auf die Kundendatei des Vortags, lädt sie über eine Pipeline, archiviert sie – und meldet einen Fehler, wenn die Datei nicht kommt oder der Import scheitert. Geprüft mit runnel validate.

Jeder Workflow hat genau eine Action core.start ohne eingehende Links. core.success beendet ihn sofort erfolgreich, core.abort als fehlgeschlagen.

Links und Bedingungen

links:
  - { from: start, to: fetch }                       # when: success (Standard)
  - { from: fetch, to: report, when: failure }
  - { from: fetch, to: cleanup, when: always }
  - { from: fetch, to: big, when: "{{ result.output.rows > 1000 }}" }
  - { from: retry-wait, to: fetch, loop: true }      # Rücksprung, ausdrücklich erlaubt
  - { from: fetch, to: notify, disabled: true }      # bleibt im Design, wird nicht ausgeführt
whenSymbolLink wird verfolgt, wenn …
success✔die Action erfolgreich war (Standard)
failure✖die Action fehlgeschlagen ist
always∞in jedem Fall
{{ … }}ƒder Ausdruck wahr ist; result ist das Ergebnis der Action davor

Hat eine Action mehrere erfüllte Links, laufen die Nachfolger parallel. Zyklen sind nur über Links mit loop: true erlaubt; eine Action läuft höchstens 10.000-mal je Lauf.

Fehler und Ergebnis

  • Ein Fehler, den kein Fehler- oder Immer-Link behandelt, lässt den Workflow fehlschlagen – andere Zweige laufen vorher zu Ende.
  • retry wiederholt eine Action, timeout begrenzt jeden Versuch, continueOnError ignoriert den Fehler.
  • core.check lässt eine Bedingung prüfen und schlägt mit eigener Meldung fehl, wenn sie falsch ist.
  • Ein Abbruch (Strg+C, Editor, Timeout des Workflows) stoppt laufende Actions, folgt keinen Fehler-Links und endet mit Status cancelled.

Join: mehrere eingehende Links

joinVerhalten
all (Standard)startet einmal, wenn alle Vorgänger entschieden sind, die noch ein Signal liefern können. Zweige, die nicht durchlaufen werden, zählen als erledigt (Status skipped).
firststartet beim ersten eingehenden Link, die weiteren werden ignoriert
eachstartet bei jedem eingehenden Link erneut

joinTimeout begrenzt bei all das Warten. Der Projektstandard steht in project.yaml unter workflow.defaultJoin. Als Sammelpunkt mehrerer Zweige eignet sich core.dummy. Beachte: join: all startet auch, wenn ein Zweig fehlgeschlagen ist – Fehlerpfade daher eigens modellieren.

Ergebnisse weiterverwenden

Viele Actions liefern Ausgabedaten, z. B. file.list die Dateien, http.request Status und Antwort, core.run-pipeline die Zähler der Transforms. In Ausdrücken:

  • result.output – Ergebnis der Action, von der ein Link ausgeht (in Link-Bedingungen)
  • results.<id>.output bzw. results["id"].output – Ergebnis einer beliebigen Action, die schon gelaufen ist

Was output enthält, steht in der Beschreibung jedes Bausteins in der Referenz.

Wiederholung je Eintrag (forEach)

Jede Action kann für jeden Eintrag einer Liste laufen – etwa eine Pipeline je Datei. Der aktuelle Eintrag heißt row.

{{snippet:guide-each.workflow.yaml|workflows/each.workflow.yaml}}
  • parallel: so viele Einträge gleichzeitig (Standard 1).
  • stopOnError: beim ersten Fehler aufhören (Standard) oder mit false alle Einträge versuchen.
  • Ergebnis: items (je Eintrag row, success, error, output), succeeded und failed.

Sub-Workflows und Pipelines aufrufen

  • core.run-workflow startet einen anderen Workflow mit params; dessen outputs sind das Ergebnis. Sein Log erscheint bei der aufrufenden Action.
  • core.run-pipeline startet eine Pipeline; Ergebnis sind die Zähler je Transform (output.transforms.<id>.read/written/errors) und output.errors. Mit rows gehen Datensätze hinein, mit core.to-result kommen sie als output.rows zurück.
  • Pfade sind relativ zum Projekt und dürfen es nicht verlassen. Ist der Pfad dynamisch (${…}), schränkt allowedTargets die erlaubten Ziele ein.
  • Übergeben werden nur die genannten Parameter; der aufgerufene Workflow sieht seine eigenen Standardwerte und die Variablen des Projekts.

User guide

Workflows

A workflow controls a process: actions run along links, in sequence or in parallel. Every action ends with success or failure, and the links decide what happens next.

Example

Waits for the previous day's customer file, loads it through a pipeline, archives it – and reports an error if the file doesn't arrive or the import fails. Checked with runnel validate.

{{snippet:guide-nightly.workflow.yaml|workflows/nightly-import.workflow.yaml}}

File layout

FieldMeaning
kind, apiVersion, nameRequired: Workflow, runnel/v1 and a name
descriptionPurpose of the workflow
parametersInputs with type, default and allowed values – see Parameters
outputsResult of the workflow: name, optional type and description, value (usually an expression); evaluated only on success
settings.timeoutMaximum duration of the whole workflow, e.g. 2h
settings.maxConcurrentRunsAt most this many concurrent runs of this workflow on the server
actions, linksThe steps and their connections
layoutPositions of the actions in the editor; no effect on execution

Unknown fields are an error – typos show up immediately, usually with a suggestion. Durations have a unit: 30s, 5m, 2h, 1h30m.

Actions

FieldMeaning
id requiredUnique in the workflow; letters, digits, - and _, starting with a letter
type requiredComponent, e.g. file.copy – all in the reference
withConfiguration of the component; values with ${…} and {{ … }}
descriptionNote on the action
timeoutMaximum duration per attempt
retryattempts (total attempts), backoff (wait before the second attempt), strategy: fixed or exponential
continueOnErrorA failure counts as success; the workflow continues on the success links
join, joinTimeoutBehavior with several incoming links – see Join
forEach, parallel, stopOnErrorRun the action per entry of a list – see Repetition

Every workflow has exactly one core.start action without incoming links. core.success ends it immediately as succeeded, core.abort as failed.

Links and conditions

links:
  - { from: start, to: fetch }                       # when: success (default)
  - { from: fetch, to: report, when: failure }
  - { from: fetch, to: cleanup, when: always }
  - { from: fetch, to: big, when: "{{ result.output.rows > 1000 }}" }
  - { from: retry-wait, to: fetch, loop: true }      # loop back, explicitly allowed
  - { from: fetch, to: notify, disabled: true }      # stays in the design, not executed
whenSymbolThe link is followed if …
success✔the action succeeded (default)
failure✖the action failed
always∞in any case
{{ … }}ƒthe expression is true; result is the result of the action before

If an action has several satisfied links, the successors run in parallel. Cycles are only allowed via links with loop: true; an action runs at most 10,000 times per run.

Errors and result

  • A failure not handled by any failure or always link makes the workflow fail – other branches finish first.
  • retry repeats an action, timeout limits each attempt, continueOnError ignores the failure.
  • core.check checks a condition and fails with its own message if it is false.
  • A cancellation (Ctrl+C, editor, workflow timeout) stops running actions, follows no failure links and ends with status cancelled.

Join: several incoming links

joinBehavior
all (default)Starts once all predecessors that can still deliver a signal have decided. Branches that are not taken count as done (status skipped).
firstStarts on the first incoming link; further ones are ignored
eachStarts again for every incoming link

joinTimeout limits the wait with all. The project default is workflow.defaultJoin in project.yaml. core.dummy works well as a collection point for several branches. Note: join: all also starts if a branch failed – model failure paths separately.

Using results

Many actions return output data, e.g. file.list the files, http.request status and response, core.run-pipeline the transform counts. In expressions:

  • result.output – result of the action a link starts from (in link conditions)
  • results.<id>.output or results["id"].output – result of any action that has already run

What output contains is stated in each component's description in the reference.

Repetition per entry (forEach)

Any action can run for each entry of a list – e.g. a pipeline per file. The current entry is called row.

{{snippet:guide-each.workflow.yaml|workflows/each.workflow.yaml}}
  • parallel: this many entries at once (default 1).
  • stopOnError: stop at the first error (default) or try all entries with false.
  • Result: items (per entry row, success, error, output), succeeded and failed.

Calling sub-workflows and pipelines

  • core.run-workflow starts another workflow with params; its outputs are the result. Its log appears with the calling action.
  • core.run-pipeline starts a pipeline; the result is the counts per transform (output.transforms.<id>.read/written/errors) and output.errors. Records go in with rows and come back as output.rows via core.to-result.
  • Paths are relative to the project and must not leave it. If the path is dynamic (${…}), allowedTargets restricts the allowed targets.
  • Only the named parameters are passed; the called workflow sees its own defaults and the project's variables.
