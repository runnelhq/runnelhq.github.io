Runnel entwickeln

Runnel ist in Go geschrieben und besteht aus einer einzigen runnel.exe. Diese Seiten richten sich an alle, die am Kern mitarbeiten oder eigene Bausteine entwickeln – Menschen wie KI-Agenten.

Stand: main vom 19.11.2026 · Quelle: CONTRIBUTING.md, AGENTS.md. Bei Abweichungen gilt das Repository.

Actions entwickeln Neue Bausteine für Workflows: Typname, Konfiguration, Execute, Tests und Checkliste.
Transforms entwickeln Bausteine für Pipelines. Die Anleitung folgt mit den Roadmap-Schritten S12/S13.
Plugins entwickeln Bausteine in beliebiger Sprache über JSON-RPC. Die Anleitung folgt mit S49–S51.

Schnellstart

Voraussetzungen: Go in der Version aus go.mod (derzeit Go 1.26), golangci-lint v2.15.0 für make lint und make – unter Windows zum Beispiel über Git Bash. Alle Befehle funktionieren auch ohne make, siehe README.

git clone https://github.com/runnelhq/runnel.git
cd runnel
make build                    # bin/runnel
make test                     # Tests mit Race-Detector
bin/runnel validate examples
bin/runnel run -v examples/hello/workflows/hello.workflow.yaml

Konventionen

SpracheCode, Kommentare, CLI-Ausgaben und Fehlermeldungen englisch; Dokumentation, ADRs und PR-Beschreibungen deutsch.
Typnamen<namensraum>.<name>; Actions und Transforms haben getrennte Namensräume, kein -transform-Suffix (ADR 0013).
MeldungenFehler in Dateien mit Position: datei:zeile:spalte: error|warning: text – für Anwender verständlich, ohne Go-Typnamen.
TestsGolden-Files für Formate und Ausgaben, t.TempDir() statt echter Pfade, plattformunabhängig – die CI läuft unter Linux und Windows.
Windows-firstPfade über path/filepath, UNC-Pfade, Kodierungen (BOM, UTF-16) und CRLF berücksichtigen.
Kein VorgriffNur umsetzen, was der aktuelle Roadmap-Schritt verlangt. Nicht Unterstütztes klar melden statt still ignorieren.

Ablauf eines Beitrags

  1. Thema wählen: einen offenen Schritt aus der Roadmap oder ein Issue. Größere Vorhaben vorher in einem Issue abstimmen.
  2. Branch anlegen von main.
  3. Umsetzen und klein halten: ein Roadmap-Schritt bzw. ein Thema je Pull Request, Richtwert höchstens ca. 1.000 geänderte Zeilen inklusive Tests.
  4. Prüfen: make lint und make test, bei Parser-Änderungen zusätzlich make fuzz.
  5. Pull Request nach main mit deutscher Beschreibung: Zusammenfassung, Änderungen, Entscheidungen fürs Review und „Prüfen“ – wie man das Ergebnis selbst ausprobiert.
  6. CI und Review: Lint, Schwachstellen-Check, Tests unter Linux und Windows, Build und Packen. Gemergt wird bei grüner CI und abgeschlossenem Review.

Regeln

  • Tests gehören zum PR: Unit-Tests, Golden-File-Tests für Formate und Ausgaben, -race für nebenläufigen Code.
  • Doku gehört zum PR: Konzept, Roadmap (Schritt mit ✅ markieren), ADRs, README und Anleitungen unter docs/dev/ im selben PR anpassen.
  • Grundsätzliche Entscheidungen – Formate, Semantik, neue Abhängigkeiten, Namensregeln – als ADR festhalten und vorher mit dem Maintainer abstimmen.
  • Abhängigkeiten nur mit Begründung, MIT-kompatibler Lizenz (ADR 0004) und fest gepinnter Version.
  • Nicht tun: Tests überspringen oder abschwächen, um die CI grün zu bekommen; Golden-Dateien ohne Prüfung überschreiben; Secrets in Code, Tests oder Logs; Release- und CI-Workflows ohne Auftrag ändern.

Hinweise für KI-Agenten

Für Coding-Agenten wie Claude Code, Copilot oder Codex fasst AGENTS.md im Repository dieselben Regeln kompakt zusammen; CLAUDE.md verweist darauf. Agenten arbeiten nach denselben Regeln wie Menschen – insbesondere „ein Roadmap-Schritt = ein PR“ und „Doku im selben PR“.

Weiterführend

  • Konzept und Architektur
  • Roadmap
  • Testplan und bekannte Einschränkungen
  • Architekturentscheidungen (ADR)
  • Fehler melden – mit runnel version, Windows-Version, Workflow (ohne Secrets) und vollständiger Ausgabe

Developing Runnel

Runnel is written in Go and ships as a single runnel.exe. These pages are for everyone who works on the core or builds their own components – humans and AI agents alike.

As of main on 2026-11-19 · Source (German): CONTRIBUTING.md, AGENTS.md. If anything differs, the repository is authoritative.

Developing actions New workflow components: type name, configuration, Execute, tests and checklist.
Developing transforms Pipeline components. The guide follows with roadmap steps S12/S13.
Developing plugins Components in any language via JSON-RPC. The guide follows with S49–S51.

Quick start

Prerequisites: Go as specified in go.mod (currently Go 1.26), golangci-lint v2.15.0 for make lint, and make – on Windows e.g. via Git Bash. Every command also works without make, see the README.

git clone https://github.com/runnelhq/runnel.git
cd runnel
make build                    # bin/runnel
make test                     # tests with race detector
bin/runnel validate examples
bin/runnel run -v examples/hello/workflows/hello.workflow.yaml

Conventions

LanguageCode, comments, CLI output and error messages in English; documentation, ADRs and PR descriptions in German.
Type names<namespace>.<name>; actions and transforms have separate namespaces, no -transform suffix (ADR 0013).
MessagesErrors in files carry a position: file:line:column: error|warning: text – understandable for users, no Go type names.
TestsGolden files for formats and output, t.TempDir() instead of real paths, platform-independent – CI runs on Linux and Windows.
Windows firstUse path/filepath; handle UNC paths, encodings (BOM, UTF-16) and CRLF.
No anticipationOnly implement what the current roadmap step requires. Report what is unsupported instead of silently ignoring it.

How to contribute

  1. Pick a topic: an open step from the roadmap or an issue. Discuss larger changes in an issue first.
  2. Create a branch from main.
  3. Implement and keep it small: one roadmap step or topic per pull request, roughly 1,000 changed lines at most, tests included.
  4. Check: make lint and make test; for parser changes also make fuzz.
  5. Pull request to main with a German description: summary, changes, decisions for the review and “Prüfen” – how to try the result yourself.
  6. CI and review: lint, vulnerability check, tests on Linux and Windows, build and packaging. Merged when CI is green and the review is done.

Rules

  • Tests belong in the PR: unit tests, golden-file tests for formats and output, -race for concurrent code.
  • Docs belong in the PR: update concept, roadmap (mark the step with ✅), ADRs, README and the guides in docs/dev/ in the same PR.
  • Fundamental decisions – formats, semantics, new dependencies, naming rules – are recorded as an ADR and agreed with the maintainer first.
  • Dependencies only with a reason, an MIT-compatible license (ADR 0004) and a pinned version.
  • Don't: skip or weaken tests to get CI green; overwrite golden files without review; put secrets in code, tests or logs; change release or CI workflows without being asked.

Notes for AI agents

For coding agents such as Claude Code, Copilot or Codex, AGENTS.md in the repository sums up the same rules; CLAUDE.md points to it. Agents follow the same rules as humans – in particular “one roadmap step = one PR” and “docs in the same PR”.
