Plugins

Plugins ergänzen Runnel um Actions, Transforms und Connection-Typen, die nicht in die exe gehören – etwa für ein Verzeichnis, ein ERP oder ein Fachverfahren. Ein Plugin ist ein eigenes Programm im Projektordner; im Editor und in den Dateien verhält es sich wie die eingebauten Bausteine.

So funktioniert es

  • Im Projekt: Jedes Plugin liegt in plugins/<name>/ mit einer plugin.yaml und seinem Programm. Plugins gelten nur für dieses Projekt; ein Projektordner enthält so alles, was er zum Laufen braucht.
  • Eigener Prozess: Runnel startet das Plugin bei Bedarf als Kindprozess und spricht über stdin/stdout mit ihm – ohne offenen Port. Je Lauf gibt es einen Prozess je Plugin; er endet mit dem Lauf. Stürzt ein Plugin ab, scheitert der Lauf, nicht der Server.
  • Eigener Namensraum: Die Typen eines Plugins beginnen mit seinem Namensraum, z. B. ldap.search. Eingebaute Namensräume wie core oder http kann ein Plugin nicht belegen.
  • Erst nach Freigabe: Ein Plugin ist Code mit den Rechten von Runnel. Runnel startet es erst, wenn es auf diesem Rechner für dieses Projekt freigegeben ist – ein geklontes Projekt führt beim Öffnen oder Prüfen also keinen fremden Code aus.

Installieren

  1. Archiv laden und prüfen: von den Releases des Plugins das Archiv für das System, z. B. runnel-plugin-iban_<version>_windows_amd64.zip, dazu SHA256SUMS; <version> steht für die Version des Plugins. Die Prüfsumme vergleichen; die Herkunft prüft auf Wunsch gh attestation verify <archiv> --repo runnelhq/plugin-iban.
  2. In das Projekt entpacken, sodass plugins/iban/plugin.yaml entsteht.
  3. Freigeben mit runnel plugins trust (siehe unten) oder im Editor.
  4. Prüfen: runnel plugins zeigt das Plugin als trusted mit seinen Typen; runnel validate prüft die Dateien, die sie nutzen.
Get-FileHash .\runnel-plugin-iban_<version>_windows_amd64.zip -Algorithm SHA256
Expand-Archive .\runnel-plugin-iban_<version>_windows_amd64.zip -DestinationPath D:\flows\plugins
runnel plugins trust D:\flows --plugin iban
runnel plugins D:\flows
plugins\
  iban\
    plugin.yaml           # Name, Version, Namensraum, Programm je Betriebssystem
    README.md             # Anleitung, im Editor lesbar
    bin\iban.exe
    LICENSE
    THIRD_PARTY_NOTICES

Trust plugin iban? [y/N] y
Plugin iban is trusted.
  • Hash: Die Freigabe gilt einem Stand des ganzen Plugin-Ordners (SHA-256 über alle Dateien). Jede Änderung – auch ein Update – hebt sie auf; runnel plugins zeigt dann changed since trusted, und Läufe, die das Plugin brauchen, starten nicht.
  • Optionen: --plugin <name> wählt einzelne Plugins, --yes gibt ohne Rückfrage frei (für Skripte). runnel plugins untrust D:\flows --plugin iban nimmt die Freigabe zurück.
  • Wo: Freigaben stehen nie im Projekt, sondern beim Benutzer in %AppData%\runnel\trusted-plugins.json.
  • Windows-Dienst: Der Dienst hat eigene Freigaben in %ProgramData%\runnel\trust\plugins.json, die nur Administratoren ändern: runnel plugins trust --service D:\flows in einer Konsole „als Administrator“. runnel plugins zeigt trusted (service).

Nutzen

Die Typen eines freigegebenen Plugins stehen in Workflows, Pipelines und Connections bereit wie eingebaute; Runnel prüft die Felder gegen das Schema des Plugins und löst Variablen, Ausdrücke und Connections vorher auf.

# Workflow: Ergebnis unter results.check.output
- id: check
  type: iban.validate
  with:
    iban: ${IBAN}

# Pipeline: Transform mit Fehler-Link
- id: users
  type: ldap.input
  with:
    connection: ad
    filter: (objectClass=user)

# connections/ad.yaml: Connection-Typ des Plugins
kind: Connection
apiVersion: runnel/v1
name: ad
type: ldap
with:
  url: ldaps://dc1.example.com
  bindDn: svc-runnel@example.com
  password: ${secret:AD_PASSWORD}
  • Ist ein Plugin nicht freigegeben oder geändert, melden runnel validate und der Editor das am Schritt bzw. an der Connection: „plugin "iban" is not trusted on this computer“.
  • Was das Plugin auf stderr schreibt, steht im Log des Laufs; Secrets sind darin, in Fehlern und Ergebnissen maskiert.
  • Welche Felder ein Typ hat, steht in der Anleitung des Plugins (README.md im Plugin-Ordner) und im Eigenschafts-Panel des Editors.

Im Editor

  • Explorer: Plugin-Ordner tragen einen Stecker, ihre Version und ihren Stand: ✓ freigegeben, ! nicht freigegeben oder geändert, ✕ startet nicht.
  • Übersicht: Ein Klick öffnet plugin.yaml als Übersicht („Overview | YAML“) mit Freigaben für Konto und Dienst, Typen, „Used by“ (wo das Projekt sie nutzt) und Programm.
  • Freigeben: „Trust…“ zeigt Ordner, Programm, Dateien und Hash wie runnel plugins trust und gibt das Plugin für das Konto frei, unter dem runnel serve läuft. „Untrust“ nimmt die Freigabe zurück, „Try again“ startet ein Plugin nach einem Fehler neu. Im Dienst zeigt der Editor stattdessen den Befehl für Administratoren.
  • Palette: Typen ohne eingebaute Kategorie stehen in einer eigenen Gruppe „Plugin: <name>“. Ein Schritt eines nicht nutzbaren Plugins zeigt im Panel und unter „Problems“ den Grund mit „Open plugin …“.

Aktualisieren und entfernen

  • Update: den Ordner plugins/<name>/ durch den Inhalt des neuen Archivs ersetzen, dann erneut runnel plugins trust (beim Dienst mit --service).
  • Entfernen: runnel plugins untrust D:\flows --plugin <name>, dann den Ordner löschen.
  • Versionen von Plugins sind unabhängig von Runnel. Die Anleitung jedes Plugins nennt, ab welchem Stand von Runnel es läuft.

Eigene Plugins

Plugins lassen sich in jeder Sprache schreiben, die stdin und stdout lesen kann. Für Go und Rust gibt es SDKs – sdk-go und sdk-rust; damit sind auch die offiziellen Plugins gebaut. Eigene Plugins bekommen einen Namensraum mit Präfix der Firma (z. B. contoso-sap). Wie es geht: Plugins entwickeln in der Entwicklerdoku.

User guide

Plugins

Plugins add actions, transforms and connection types to Runnel that do not belong in the executable – for a directory, an ERP or a specialist system, say. A plugin is a program of its own in the project folder; in the editor and in the files it behaves like the built-in components.

How it works

  • In the project: each plugin lives in plugins/<name>/ with a plugin.yaml and its program. Plugins apply to this project only; that way a project folder contains everything it needs to run.
  • A process of its own: Runnel starts the plugin when needed as a child process and talks to it over stdin/stdout – no open port. There is one process per plugin and run; it ends with the run. If a plugin crashes, the run fails, not the server.
  • Its own namespace: a plugin's types start with its namespace, e.g. ldap.search. A plugin cannot take built-in namespaces such as core or http.
  • Only once trusted: a plugin is code with Runnel's rights. Runnel starts it only once it is trusted on this computer for this project – so a cloned project runs no foreign code when it is opened or validated.

Installing

  1. Download and check the archive: from the plugin's releases, the archive for your system, e.g. runnel-plugin-iban_<version>_windows_amd64.zip, plus SHA256SUMS; <version> stands for the plugin version. Compare the checksum; optionally check the origin with gh attestation verify <archive> --repo runnelhq/plugin-iban.
  2. Unpack it into the project so that plugins/iban/plugin.yaml exists.
  3. Trust it with runnel plugins trust (see below) or in the editor.
  4. Check: runnel plugins shows the plugin as trusted with its types; runnel validate checks the files that use them.
Get-FileHash .\runnel-plugin-iban_<version>_windows_amd64.zip -Algorithm SHA256
Expand-Archive .\runnel-plugin-iban_<version>_windows_amd64.zip -DestinationPath D:\flows\plugins
runnel plugins trust D:\flows --plugin iban
runnel plugins D:\flows
plugins\
  iban\
    plugin.yaml           # name, version, namespace, program per operating system
    README.md             # guide, readable in the editor
    bin\iban.exe
    LICENSE
    THIRD_PARTY_NOTICES

Trusting

  folder:  D:\flows\plugins\iban
  program: bin/iban.exe
  hash:    sha256:9e18427e5e7af639ea431e7d855f126ad277fa383646e3769359eaeca6705154

Trust plugin iban? [y/N] y
Plugin iban is trusted.
  • Hash: an approval applies to one state of the whole plugin folder (SHA-256 over all files). Any change – an update too – voids it; runnel plugins then shows changed since trusted, and runs that need the plugin do not start.
  • Options: --plugin <name> picks single plugins, --yes trusts without asking (for scripts). runnel plugins untrust D:\flows --plugin iban withdraws the approval.
  • Where: approvals are never stored in the project but with the user in %AppData%\runnel\trusted-plugins.json.
  • Windows service: the service has its own approvals in %ProgramData%\runnel\trust\plugins.json, which only administrators change: runnel plugins trust --service D:\flows in a console “as administrator”. runnel plugins shows trusted (service).

Using

The types of a trusted plugin are available in workflows, pipelines and connections like built-in ones; Runnel checks the fields against the plugin's schema and resolves variables, expressions and connections beforehand.

# Workflow: result under results.check.output
- id: check
  type: iban.validate
  with:
    iban: ${IBAN}

# Pipeline: transform with error link
- id: users
  type: ldap.input
  with:
    connection: ad
    filter: (objectClass=user)

# connections/ad.yaml: the plugin's connection type
kind: Connection
apiVersion: runnel/v1
name: ad
type: ldap
with:
  url: ldaps://dc1.example.com
  bindDn: svc-runnel@example.com
  password: ${secret:AD_PASSWORD}
  • If a plugin is not trusted or has changed, runnel validate and the editor report it on the step or connection: “plugin "iban" is not trusted on this computer”.
  • What the plugin writes to stderr appears in the run log; secrets are masked there and in errors and results.
  • The fields of a type are described in the plugin's guide (README.md in the plugin folder) and in the editor's properties panel.

In the editor

  • Explorer: plugin folders carry a plug, their version and their state: ✓ trusted, ! not trusted or changed, ✕ does not start.
  • Overview: a click opens plugin.yaml as an overview (“Overview | YAML”) with approvals for account and service, types, “Used by” (where the project uses them) and program.
  • Trusting: “Trust…” shows folder, program, files and hash like runnel plugins trust and trusts the plugin for the account runnel serve runs as. “Untrust” withdraws the approval, “Try again” restarts a plugin after an error. In the service, the editor shows the command for administrators instead.
  • Palette: types without a built-in category appear in a group of their own, “Plugin: <name>”. A step of an unusable plugin shows the reason with “Open plugin …” in the panel and under “Problems”.

Updating and removing

  • Update: replace the folder plugins/<name>/ with the contents of the new archive, then run runnel plugins trust again (with --service for the service).
  • Remove: runnel plugins untrust D:\flows --plugin <name>, then delete the folder.
  • Versions of plugins are independent of Runnel. Each plugin's guide names the Runnel state it needs.

Your own plugins

Plugins can be written in any language that can read stdin and write stdout. For Go and Rust there are SDKs – sdk-go and sdk-rust; the official plugins are built with them too. Your own plugins get a namespace with a company prefix (e.g. contoso-sap). How it works: Developing plugins in the developer docs.
