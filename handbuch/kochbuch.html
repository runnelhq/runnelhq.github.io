Handbuch · Kochbuch

Kochbuch

Rezepte für Anbindungen, Dateien und Datenbanken. Runnel bringt keine hunderte fertigen Konnektoren mit, sondern einen generischen HTTP-Baustein und eine Connection für Adresse und Anmeldung. Die Rezepte zeigen, wie man damit bekannte APIs anbindet – als lesbare Dateien, die man übernimmt und anpasst.

Rezepte

RezeptAnmeldungzeigt
Wetter (Open-Meteo)keineerste Anfrage, Antwort lesen, Outputs
Microsoft TeamsSignatur in der Adresse (apiKey in der Query)Nachricht als Karte, Sub-Workflow als Connector, Meldung bei Fehlern
GitHubToken (bearer)Paginierung über den Header Link, Daten anlegen
HubSpotToken einer Private App (bearer)Paginierung mit Cursor, Kontakt anlegen
Lexware OfficeAPI-Schlüssel (bearer)Paginierung mit Seitennummer, Rate-Limit mit Retry-After
SharePoint (Microsoft Graph)OAuth2 Client CredentialsDownload mit saveTo, ZIP entpacken, Pipeline je Datei
Rezept für Dateienzeigt
Excel lesen und schreibenBlatt und Bereich lesen, typisierte Werte, formatierte Mappe schreiben, Fehler-Link
XML-AustauschElemente als Datensätze, Attribute und verschachtelte Elemente lesen und schreiben

Jedes Rezept ist ein kleines, vollständiges Projekt: project.yaml, Connection, Workflows und Pipelines, bei Datei-Rezepten mit Beispieldaten. Alle Dateien sind mit runnel validate geprüft; API-Rezepte laufen gegen einen Testserver, der die API nachbildet, Datei-Rezepte vollständig mit ihren Beispieldaten. Die Quellen liegen auf GitHub.

Übernehmen: Ordner des Rezepts in ein eigenes Projekt kopieren – oder nur die Connection und die Workflows übernehmen – und die Werte unter „Anpassen“ setzen. APIs ändern sich; vor dem produktiven Einsatz die Anfragen mit der aktuellen Dokumentation des Anbieters abgleichen.

Die Connection http

Eine Connection beschreibt eine API einmal für das ganze Projekt: Basisadresse, feste Header und Anmeldung. Workflows nennen sie mit connection: und geben nur noch den Pfad an.

connections/shop.yaml
kind: Connection
apiVersion: runnel/v1
name: shop
type: http
with:
  baseUrl: https://api.example.com/v1/
  auth: bearer
  token: ${secret:SHOP_TOKEN}
  headers:
    Accept: application/json
Action
- id: orders
  type: http.request
  with:
    connection: shop
    url: orders            # ergibt https://api.example.com/v1/orders
    query: { status: open }
authFeldertypisch für
none–offene APIs
bearertokenPersonal Access Tokens, API-Schlüssel als Authorization: Bearer
basicuser, passwordJira, ServiceNow, ältere APIs
apiKeyapiKey, apiKeyName (Standard X-API-Key), apiKeyIn: header oder querySchlüssel in einem eigenen Header oder in der Adresse
oauth2tokenUrl, clientId, clientSecret, scopeMicrosoft Graph, Personio, Salesforce (Client Credentials)
  • Secrets stehen als ${secret:NAME} in token, password, apiKey, clientSecret und in den headers der Connection – nie in Workflows. Sie werden in Log, Fehlern und Ergebnissen maskiert. Woher sie kommen, legt das Environment fest, siehe Secrets.
  • Nur an den eigenen Host: Eine absolute url zu einem anderen Host ist ein Fehler. Mit Anmeldung ist http:// nur zum eigenen Rechner erlaubt.
  • Header: zuerst die der Connection, dann die der Action, zuletzt die Anmeldung.
  • OAuth2: Runnel holt das Token selbst, hält es bis kurz vor Ablauf im Speicher und holt nach 401 einmal ein neues.

Die Antwort lesen

http.request liefert status, headers und body; JSON ist bereits als Wert gelesen. Folgende Actions greifen mit results.<id>.output.body… darauf zu. Ab Status 400 schlägt die Action fehl – mit failOnError: false steht der Status stattdessen nur im Ergebnis, z. B. um 404 als „nicht gefunden“ zu behandeln.

Paginierung

Mit paginate liest http.request alle Seiten und liefert statt body die Felder items (alle Einträge), count und pages.

stylenächste Seite steht …Rezept
linkim Header Link: …; rel="next"GitHub
urlals Adresse im Body, z. B. @odata.nextLinkMicrosoft Graph, OData – siehe SharePoint
cursorals Wert im Body, der als Query-Parameter zurückgehtHubSpot
pageals fortlaufende SeitennummerLexware Office
offsetals Zahl der bisher gelesenen Einträgeviele SQL-nahe APIs

Weitere Felder: items (Pfad zur Liste im Body), next (Pfad zur Adresse oder zum Cursor), param, start, size und sizeParam. Grenzen schützen vor Endlosschleifen und Speicherüberlauf: maxPages (Standard 100) und maxItems (Standard 10.000); mehr ist ein Fehler. Folgeseiten werden nur auf demselben Host angefragt.

Rate-Limits

Antwortet eine API mit 429 oder 503 und dem Header Retry-After, wartet http.request und fragt erneut – standardmäßig bis zu 3-mal und je höchstens eine Minute (retryAfter.maxRetries, retryAfter.maxWait). Bei Paginierung gilt das je Seite. Ohne den Header hilft retry an der Action, z. B. retry: { attempts: 3, backoff: 2s, strategy: exponential }.

Sub-Workflow als Connector

Was bei anderen Werkzeugen ein fertiger Knoten ist, ist in Runnel ein kleiner Workflow mit Parametern und Outputs, z. B. create-contact.workflow.yaml mit dem Parameter EMAIL und dem Output ID. Andere Workflows rufen ihn mit core.run-workflow auf und lesen das Ergebnis aus results.<id>.output. So bleibt die Anbindung an einer Stelle, und sie lässt sich einzeln testen: runnel run --param EMAIL=… workflows/create-contact.workflow.yaml.

Aufbau eines Rezepts

  • Zweck und Voraussetzungen: Konto, Token, Variablen und Secrets
  • Dateien: Projekt, Connection, Workflows – mit runnel validate geprüft
  • Ausführen und Anpassen
  • Stand: womit das Rezept geprüft ist und wann

User guide · Cookbook

Cookbook

Recipes for connecting APIs, files and databases. Runnel doesn't ship hundreds of ready-made connectors but a generic HTTP component and a connection for address and sign-in. The recipes show how to connect well-known APIs with them – as readable files you take over and adapt.

Recipes

RecipeSign-inShows
Weather (Open-Meteo)noneFirst request, reading the response, outputs
Microsoft TeamsSignature in the address (apiKey in the query)Message as a card, sub-workflow as a connector, notification on failure
GitHubToken (bearer)Pagination via the Link header, creating data
HubSpotPrivate app token (bearer)Cursor pagination, creating a contact
Lexware OfficeAPI key (bearer)Page-number pagination, rate limit with Retry-After
SharePoint (Microsoft Graph)OAuth2 client credentialsDownload with saveTo, unpacking a ZIP, a pipeline per file
Recipe for filesShows
Reading and writing ExcelReading sheet and range, typed values, writing a formatted workbook, error link
XML exchangeElements as records, reading and writing attributes and nested elements

Every recipe is a small, complete project: project.yaml, connection, workflows and pipelines, with sample data for file recipes. All files are checked with runnel validate; API recipes run against a test server that mimics the API, file recipes run completely with their sample data. The sources are on GitHub.

Taking it over: copy the recipe folder into your own project – or only the connection and workflows – and set the values under “Adapting”. APIs change; check the requests against the provider's current documentation before production use.

The http connection

A connection describes an API once for the whole project: base address, fixed headers and sign-in. Workflows name it with connection: and only give the path.

connections/shop.yaml
kind: Connection
apiVersion: runnel/v1
name: shop
type: http
with:
  baseUrl: https://api.example.com/v1/
  auth: bearer
  token: ${secret:SHOP_TOKEN}
  headers:
    Accept: application/json
Action
- id: orders
  type: http.request
  with:
    connection: shop
    url: orders            # becomes https://api.example.com/v1/orders
    query: { status: open }
authFieldsTypical for
none–Open APIs
bearertokenPersonal access tokens, API keys as Authorization: Bearer
basicuser, passwordJira, ServiceNow, older APIs
apiKeyapiKey, apiKeyName (default X-API-Key), apiKeyIn: header or queryKeys in a custom header or in the address
oauth2tokenUrl, clientId, clientSecret, scopeMicrosoft Graph, Personio, Salesforce (client credentials)
  • Secrets go as ${secret:NAME} into token, password, apiKey, clientSecret and the connection's headers – never into workflows. They are masked in log, errors and results. The environment decides where they come from, see Secrets.
  • Own host only: an absolute url to another host is an error. With a sign-in, http:// is only allowed to the local machine.
  • Headers: the connection's first, then the action's, finally the sign-in.
  • OAuth2: Runnel fetches the token itself, keeps it in memory until shortly before it expires and fetches a new one once after 401.

Reading the response

http.request returns status, headers and body; JSON is already parsed. Later actions access it via results.<id>.output.body…. From status 400 the action fails – with failOnError: false the status is only in the result instead, e.g. to treat 404 as “not found”.

Pagination

With paginate, http.request reads all pages and returns items (all entries), count and pages instead of body.

styleThe next page is …Recipe
linkin the header Link: …; rel="next"GitHub
urlan address in the body, e.g. @odata.nextLinkMicrosoft Graph, OData – see SharePoint
cursora value in the body sent back as a query parameterHubSpot
pagea running page numberLexware Office
offsetthe number of entries read so farmany SQL-like APIs

Further fields: items (path to the list in the body), next (path to the address or cursor), param, start, size and sizeParam. Limits protect against endless loops and memory overflow: maxPages (default 100) and maxItems (default 10,000); more is an error. Following pages are only requested on the same host.

Rate limits

If an API answers 429 or 503 with a Retry-After header, http.request waits and asks again – by default up to 3 times and at most one minute each (retryAfter.maxRetries, retryAfter.maxWait). With pagination this applies per page. Without the header, retry on the action helps, e.g. retry: { attempts: 3, backoff: 2s, strategy: exponential }.

Sub-workflow as a connector

What other tools ship as a ready-made node is a small workflow with parameters and outputs in Runnel, e.g. create-contact.workflow.yaml with the parameter EMAIL and the output ID. Other workflows call it with core.run-workflow and read the result from results.<id>.output. The integration stays in one place and can be tested on its own: runnel run --param EMAIL=… workflows/create-contact.workflow.yaml.

Structure of a recipe

  • Purpose and prerequisites: account, token, variables and secrets
  • Files: project, connection, workflows – checked with runnel validate
  • Running and adapting
  • Status: what the recipe was checked with and when
