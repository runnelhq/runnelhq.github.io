Handbuch

Projekt und Konfiguration

Was sich zwischen Test und Produktion unterscheidet – Pfade, Server, Zugangsdaten – steht nicht in den Workflows, sondern in Environments, Variablen, Secrets und Connections.

Projekt (project.yaml)

Runnel findet das Projekt über project.yaml im Ordner der Datei oder einem übergeordneten Ordner – wie Git den Ordner .git.

project.yaml
kind: Project
apiVersion: runnel/v1
name: flows
description: Datenflüsse der Buchhaltung
defaultEnvironment: dev
variables:
  BASE: D:\data
  INBOX: ${BASE}\inbox
  ARCHIVE: ${BASE}\archive
settings:
  maxConcurrentRuns: 4
workflow:
  defaultJoin: all
FeldBedeutung
name, descriptionName und Zweck des Projekts; erscheinen im Editor
defaultEnvironmentEnvironment, wenn ein Lauf keines nennt, z. B. dev
variablesVariablen für alle Environments; Werte dürfen andere Variablen enthalten
secretStore, secretsWoher ${secret:…} liest, falls ein Environment nichts festlegt – siehe Secrets
settings.maxConcurrentRunshöchstens so viele Läufe des Projekts gleichzeitig auf dem Server; 0 = keine Grenze
workflow.defaultJoinStandard für Actions mit mehreren eingehenden Links: all, first oder each – siehe Join

Environments

Ein Environment überschreibt Variablen für eine Umgebung. Der Name muss dem Dateinamen entsprechen. Gewählt wird es mit --env, im Editor beim Start oder im Trigger; sonst gilt defaultEnvironment.

environments/prod.yaml
kind: Environment
apiVersion: runnel/v1
name: prod
description: Produktivserver
variables:
  BASE: \\fileserver\data
secretStore: env

Variablen

SchreibweiseBedeutung
${NAME}Variable aus Projekt, Environment oder Parametern
${env:NAME}Umgebungsvariable des Betriebssystems, z. B. ${env:COMPUTERNAME}, ${env:TEMP}
${secret:NAME}Secret – nur in bestimmten Feldern, siehe unten
${PROJECT_DIR}eingebaut: absoluter Pfad des Projektordners
$${ein wörtliches ${

Gibt es denselben Namen auf mehreren Ebenen, gewinnt die spätere:

  1. Eingebaut: PROJECT_DIR
  2. Standardwerte der Parameter (parameters[].default)
  3. Projekt (project.yaml, variables)
  4. Environment (environments/<name>.yaml)
  5. Beim Start übergebene Parameter: --param, Editor, Trigger, HTTP-Anfrage oder aufrufende Action

Werte dürfen selbst Variablen enthalten (INBOX: ${BASE}\inbox); Zyklen sind ein Fehler. runnel validate warnt je Environment vor nicht definierten Variablen – so fällt auf, wenn eine Variable nur in dev gesetzt ist.

Relative Pfade

Relative Pfade in Actions, Transforms und Triggern beziehen sich immer auf den Projektordner – ohne Projekt auf den Ordner der Datei –, nie auf das Arbeitsverzeichnis. So verhält sich ein Workflow aus der Aufgabenplanung, dem Dienst und dem Editor gleich.

Parameter

Parameter sind die Eingaben eines Workflows oder einer Pipeline. Sie haben einen Typ und optional erlaubte Werte; Standardwerte und übergebene Werte werden geprüft.

Parameter
parameters:
  - name: DAYS
    description: Wie viele Tage zurück
    type: integer
    default: "1"
  - name: MODE
    enum: [full, delta]
    default: delta
  - name: CUSTOMER
    required: true
FeldBedeutung
nameBuchstaben, Ziffern und _, nicht mit einer Ziffer beginnend
typestring (Standard), integer, number, boolean, json
enumerlaubte Werte
defaultStandardwert, auch als Ausdruck, z. B. "{{ formatDate(today(), 'yyyy-MM-dd') }}"
requiredmuss beim Start übergeben werden
descriptionBeschreibung, z. B. für den Startdialog im Editor

Als Variable ${DAYS} ist der Wert immer Text; in Ausdrücken liefert params.DAYS ihn mit seinem Typ.

Secrets

Passwörter und Tokens stehen nie direkt im Workflow, sondern als ${secret:NAME} oder ${secret:QUELLE/NAME}. Erlaubt ist das nur in Feldern für Secrets (z. B. password einer Connection) und als Token von HTTP-Triggern – nicht über eine Variable. Ein fehlendes Secret verhindert den Start; Werte werden in Log, Fehlern und Ergebnissen maskiert.

QuelleWoher der Wert kommt
envaus einer Umgebungsvariablen des Rechners bzw. Dienstkontos – für den Betrieb
inlineim Klartext unter secrets: im Environment oder in project.yaml – nur für Entwicklung und einfache APIs; validate warnt
locallokaler, verschlüsselter Store – geplant

Die Standardquelle legt secretStore: im Environment fest, sonst in project.yaml. So schreibt der Workflow überall ${secret:ERP_PASSWORD}, und nur das Environment entscheidet, woher der Wert kommt:

environments/dev.yaml
kind: Environment
apiVersion: runnel/v1
name: dev
secretStore: inline
secrets:
  ERP_PASSWORD: entwicklung123
environments/prod.yaml
kind: Environment
apiVersion: runnel/v1
name: prod
secretStore: env          # liest die Umgebungsvariable ERP_PASSWORD

Connections

Eine Connection beschreibt den Zugang zu einer Datenbank einmal für das ganze Projekt. Bausteine nennen sie mit connection: <name>; validate prüft, ob es sie gibt und ob der Typ passt. Unterschiede zwischen Environments kommen über Variablen.

connections/erp.yaml
kind: Connection
apiVersion: runnel/v1
name: erp                       # = Dateiname
description: ERP-Datenbank, nur lesen
type: sqlserver
with:
  host: ${ERP_HOST}
  database: ERP
  user: runnel_read
  password: ${secret:ERP_PASSWORD}

SQLite (sqlite)

path PflichtDatenbankdatei, relativ zum Projektordner; wird mit Ordner angelegt, wenn sie fehlt
readOnlynur lesend öffnen (Standard false)

SQL Server (sqlserver)

host, database PflichtServer und Datenbank
port / instanceTCP-Port (Standard 1433) oder benannte Instanz wie SQLEXPRESS (braucht den SQL Server Browser)
user, passwordSQL-Server-Anmeldung; ohne user das Windows-Konto, unter dem Runnel läuft (nur Windows)
encrypttrue (Standard), strict (TDS 8) oder false (nur die Anmeldung)
trustServerCertificatejedes Zertifikat akzeptieren, z. B. selbst signiert; validate warnt
connectTimeoutlängste Zeit für den Verbindungsaufbau, Standard 30s

PostgreSQL (postgres)

host, database, user PflichtServer, Datenbank und Benutzer
portStandard 5432
passwordals ${secret:NAME}
sslModeverify-full (Standard), verify-ca, require oder disable
connectTimeoutStandard 30s

SQL bekommt Werte nur als Parameter (@name mit dem Feld params), nie als Text im SQL – das schützt vor SQL-Injection. Beispiel: db.execute.

User guide

Project and configuration

What differs between test and production – paths, servers, credentials – does not live in the workflows but in environments, variables, secrets and connections.

Project (project.yaml)

Runnel finds the project via project.yaml in the file's folder or a parent folder – like Git finds .git.

project.yaml
kind: Project
apiVersion: runnel/v1
name: flows
description: Accounting data flows
defaultEnvironment: dev
variables:
  BASE: D:\data
  INBOX: ${BASE}\inbox
  ARCHIVE: ${BASE}\archive
settings:
  maxConcurrentRuns: 4
workflow:
  defaultJoin: all
FieldMeaning
name, descriptionName and purpose of the project; shown in the editor
defaultEnvironmentEnvironment used when a run names none, e.g. dev
variablesVariables for all environments; values may contain other variables
secretStore, secretsWhere ${secret:…} reads from unless an environment sets its own – see Secrets
settings.maxConcurrentRunsAt most this many runs of the project at once on the server; 0 = no limit
workflow.defaultJoinDefault for actions with several incoming links: all, first or each – see Join

Environments

An environment overrides variables for one environment. Its name must match the file name. It is chosen with --env, in the editor when starting or in the trigger; otherwise defaultEnvironment applies.

environments/prod.yaml
kind: Environment
apiVersion: runnel/v1
name: prod
description: Production server
variables:
  BASE: \\fileserver\data
secretStore: env

Variables

SyntaxMeaning
${NAME}Variable from project, environment or parameters
${env:NAME}Operating system environment variable, e.g. ${env:COMPUTERNAME}, ${env:TEMP}
${secret:NAME}Secret – only in certain fields, see below
${PROJECT_DIR}Built in: absolute path of the project folder
$${A literal ${

If the same name exists on several levels, the later one wins:

  1. Built in: PROJECT_DIR
  2. Parameter defaults (parameters[].default)
  3. Project (project.yaml, variables)
  4. Environment (environments/<name>.yaml)
  5. Parameters passed at start: --param, editor, trigger, HTTP request or calling action

Values may contain variables themselves (INBOX: ${BASE}\inbox); cycles are an error. runnel validate warns about undefined variables per environment – so it shows when a variable is only set in dev.

Relative paths

Relative paths in actions, transforms and triggers always refer to the project folder – without a project to the file's folder – never to the working directory. A workflow behaves the same from Task Scheduler, the service and the editor.

Parameters

Parameters are the inputs of a workflow or pipeline. They have a type and optionally allowed values; defaults and passed values are checked.

Parameters
parameters:
  - name: DAYS
    description: How many days back
    type: integer
    default: "1"
  - name: MODE
    enum: [full, delta]
    default: delta
  - name: CUSTOMER
    required: true
FieldMeaning
nameLetters, digits and _, not starting with a digit
typestring (default), integer, number, boolean, json
enumAllowed values
defaultDefault value, also as an expression, e.g. "{{ formatDate(today(), 'yyyy-MM-dd') }}"
requiredMust be passed at start
descriptionDescription, e.g. for the start dialog in the editor

As a variable ${DAYS} the value is always text; in expressions params.DAYS returns it with its type.

Secrets

Passwords and tokens never go directly into a workflow but appear as ${secret:NAME} or ${secret:SOURCE/NAME}. This is allowed only in secret fields (e.g. a connection's password) and as the token of HTTP triggers – not via a variable. A missing secret prevents the start; values are masked in log, errors and results.

SourceWhere the value comes from
envAn environment variable of the machine or service account – for operation
inlinePlain text under secrets: in the environment or project.yaml – only for development and simple APIs; validate warns
localLocal encrypted store – planned

The default source is set by secretStore: in the environment, otherwise in project.yaml. The workflow always writes ${secret:ERP_PASSWORD}, and only the environment decides where the value comes from:

environments/dev.yaml
kind: Environment
apiVersion: runnel/v1
name: dev
secretStore: inline
secrets:
  ERP_PASSWORD: development123
environments/prod.yaml
kind: Environment
apiVersion: runnel/v1
name: prod
secretStore: env          # reads the environment variable ERP_PASSWORD

Connections

A connection describes access to a database once for the whole project. Components name it with connection: <name>; validate checks that it exists and the type fits. Differences between environments come from variables.

connections/erp.yaml
kind: Connection
apiVersion: runnel/v1
name: erp                       # = file name
description: ERP database, read only
type: sqlserver
with:
  host: ${ERP_HOST}
  database: ERP
  user: runnel_read
  password: ${secret:ERP_PASSWORD}

SQLite (sqlite)

path requiredDatabase file, relative to the project folder; created with its folder if missing
readOnlyOpen for reading only (default false)

SQL Server (sqlserver)

host, database requiredServer and database
port / instanceTCP port (default 1433) or a named instance such as SQLEXPRESS (needs SQL Server Browser)
user, passwordSQL Server login; without user the Windows account Runnel runs as (Windows only)
encrypttrue (default), strict (TDS 8) or false (login only)
trustServerCertificateAccept any certificate, e.g. self-signed; validate warns
connectTimeoutLongest time to connect, default 30s

PostgreSQL (postgres)

host, database, user requiredServer, database and user
portDefault 5432
passwordAs ${secret:NAME}
sslModeverify-full (default), verify-ca, require or disable
connectTimeoutDefault 30s

SQL receives values only as parameters (@name with the params field), never as text in the SQL – this protects against SQL injection. Example: db.execute.
