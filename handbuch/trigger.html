Handbuch

Trigger

Trigger starten Workflows und Pipelines automatisch. Sie liegen als Dateien unter triggers/ (auch in Unterordnern) und sind aktiv, solange runnel serve oder der Windows-Dienst läuft.

Gemeinsame Felder

FeldBedeutung
kind, apiVersion, nameTrigger, runnel/v1 und ein im Projekt eindeutiger Name
typecron, interval, file oder http
targetWorkflow oder Pipeline, relativ zum Projekt
environmentEnvironment des Laufs; leer: Standard-Environment
paramsfeste Werte für Parameter des Ziels
enabledfalse: bleibt im Projekt, startet aber nichts
withEinstellungen des Typs (unten); unbekannte Felder sind ein Fehler
  • Geänderte Trigger-Dateien übernimmt der Server ohne Neustart.
  • Verpasste Zeitpunkte (Server lief nicht) werden nicht nachgeholt.
  • overlap: skip (Standard) startet keinen Lauf, solange der vorige dieses Triggers noch läuft; allow erlaubt parallele Läufe.
  • runnel triggers D:\flows listet alle Trigger mit ihrem nächsten Zeitpunkt; runnel validate prüft Zeitplan, Ziel, Environment und Parameter.
runnel triggers
NAME        TYPE      SCHEDULE                      TARGET                                  NEXT
import-api  http      POST /hooks/import/{DAY}      workflows/nightly-import.workflow.yaml  on request
every15     interval  every 15m                     workflows/each.workflow.yaml            disabled
inbox       file      new customers_*.csv in inbox  pipelines/customers.pipeline.yaml       on new files
nightly     cron      0 2 * * 1-5 (Europe/Berlin)   workflows/nightly-import.workflow.yaml  2026-11-24 02:00 CET

Zeitplan (cron)

triggers/nightly.yaml
kind: Trigger
apiVersion: runnel/v1
name: nightly
description: Imports every weekday at 02:00
type: cron
target: workflows/nightly-import.workflow.yaml
environment: dev
with:
  schedule: "0 2 * * 1-5"
  timezone: Europe/Berlin
  overlap: skip
  • schedule: Minute, Stunde, Tag, Monat, Wochentag – oder Kurzformen wie @daily, @hourly.
  • timezone: z. B. Europe/Berlin; leer: Zeitzone des Rechners.

Intervall (interval)

triggers/every15.yaml
kind: Trigger
apiVersion: runnel/v1
name: every15
type: interval
target: workflows/each.workflow.yaml
enabled: false
with:
  every: 15m

every ist der Abstand (mindestens 1s). Der erste Lauf kommt einen Abstand nach dem Start des Servers.

Neue Dateien (file)

triggers/inbox.yaml
kind: Trigger
apiVersion: runnel/v1
name: inbox
type: file
target: pipelines/customers.pipeline.yaml
with:
  path: inbox
  pattern: "customers_*.csv"
  interval: 30s
  param: FILE
  mode: each
  existing: ignore
FeldBedeutung
pathOrdner, relativ zum Projekt oder absolut, auch \\server\freigabe\eingang; Unterordner werden nicht durchsucht
patternDateiname mit Platzhaltern, Groß-/Kleinschreibung egal; Standard *
intervalAbstand der Abfragen, Standard 10s
paramParameter des Ziels, der den Pfad bekommt
modeeach (Standard): ein Lauf je Datei · batch: ein Lauf mit allen neuen Dateien als JSON-Liste (Parameter vom Typ json, z. B. für forEach)
existingprocess (Standard): beim Start vorhandene Dateien verarbeiten · ignore
  • Der Ordner wird abgefragt (Polling) – das funktioniert auf Netzlaufwerken und UNC-Pfaden genauso wie lokal.
  • Eine Datei gilt als bereit, wenn sie bei zwei Abfragen nacheinander unverändert ist. So wird keine Datei verarbeitet, die noch geschrieben wird.
  • Verarbeitet ist eine Datei, sobald ihr Lauf gestartet wurde. Verschieben oder Löschen ist Sache des Workflows, z. B. mit file.move ins Archiv.
  • Welche Dateien verarbeitet sind, weiß nur der laufende Server; nach einem Neustart gilt existing erneut.

HTTP (http)

triggers/api.yaml
kind: Trigger
apiVersion: runnel/v1
name: import-api
type: http
target: workflows/nightly-import.workflow.yaml
with:
  method: POST
  path: /hooks/import/{DAY}
  auth: { token: "${secret:env/IMPORT_TOKEN}" }
  response: accepted
  maxConcurrent: 2
FeldBedeutung
method, pathGET, POST, PUT, PATCH oder DELETE und ein Pfad; Platzhalter {NAME} werden zu Parametern
auth{ token: ${secret:…} } oder ${env:…} – Aufrufer senden Authorization: Bearer <token>; auth: none muss ausdrücklich stehen
responseaccepted: sofort 202 mit der Lauf-ID · run: der Aufrufer wartet auf die Antwort des Laufs
timeoutbei run: so lange wartet der Aufrufer höchstens (Standard 30s), danach 504
maxConcurrentlaufende Läufe dieses Triggers, darüber 429
historyall, errors oder none – welche Läufe behalten werden
Aufruf (PowerShell)
curl.exe -X POST -H "Authorization: Bearer $env:IMPORT_TOKEN" http://127.0.0.1:7301/hooks/import/2026-11-22
  • Parameter kommen aus Pfad, Query und Body (JSON-Objekt oder Formular); bei gleichem Namen gilt Pfad vor Query vor Body. Feste params des Triggers gewinnen. Fehlt ein Pflichtparameter oder passt ein Typ nicht: 400, ohne Lauf.
  • Antwort aus dem Workflow (response: run): Die erste http.respond-Action antwortet mit Status, Headern und Body; ohne sie sind die outputs die Antwort (200), ein gescheiterter Lauf gibt 500.
  • Antwort aus einer Pipeline: Der Transform http.response antwortet mit den Datensätzen als JSON. Ist das Ziel eine Pipeline, darf der Body eine JSON-Liste von Objekten sein; sie kommt über core.from-result als Datensätze an.
  • In Ausdrücken steht die Anfrage als request bereit: request.method, .path, .headers, .query, .body, .client.
  • HTTP-Trigger laufen auf einem eigenen Listener, Standard 127.0.0.1:7301. Im Netz nur mit HTTPS – siehe Betrieb.

User guide

Triggers

Triggers start workflows and pipelines automatically. They are files under triggers/ (also in subfolders) and are active while runnel serve or the Windows service runs.

Common fields

FieldMeaning
kind, apiVersion, nameTrigger, runnel/v1 and a name unique in the project
typecron, interval, file or http
targetWorkflow or pipeline, relative to the project
environmentEnvironment of the run; empty: default environment
paramsFixed values for the target's parameters
enabledfalse: stays in the project but starts nothing
withSettings of the type (below); unknown fields are an error
  • The server picks up changed trigger files without a restart.
  • Missed times (server not running) are not caught up.
  • overlap: skip (default) starts no run while the trigger's previous run is still going; allow allows parallel runs.
  • runnel triggers D:\flows lists all triggers with their next time; runnel validate checks schedule, target, environment and parameters.
runnel triggers
NAME        TYPE      SCHEDULE                      TARGET                                  NEXT
import-api  http      POST /hooks/import/{DAY}      workflows/nightly-import.workflow.yaml  on request
every15     interval  every 15m                     workflows/each.workflow.yaml            disabled
inbox       file      new customers_*.csv in inbox  pipelines/customers.pipeline.yaml       on new files
nightly     cron      0 2 * * 1-5 (Europe/Berlin)   workflows/nightly-import.workflow.yaml  2026-11-24 02:00 CET

Schedule (cron)

triggers/nightly.yaml
kind: Trigger
apiVersion: runnel/v1
name: nightly
description: Imports every weekday at 02:00
type: cron
target: workflows/nightly-import.workflow.yaml
environment: dev
with:
  schedule: "0 2 * * 1-5"
  timezone: Europe/Berlin
  overlap: skip
  • schedule: minute, hour, day, month, weekday – or shortcuts such as @daily, @hourly.
  • timezone: e.g. Europe/Berlin; empty: the machine's time zone.

Interval (interval)

triggers/every15.yaml
kind: Trigger
apiVersion: runnel/v1
name: every15
type: interval
target: workflows/each.workflow.yaml
enabled: false
with:
  every: 15m

every is the distance (at least 1s). The first run comes one interval after the server starts.

New files (file)

triggers/inbox.yaml
kind: Trigger
apiVersion: runnel/v1
name: inbox
type: file
target: pipelines/customers.pipeline.yaml
with:
  path: inbox
  pattern: "customers_*.csv"
  interval: 30s
  param: FILE
  mode: each
  existing: ignore
FieldMeaning
pathFolder, relative to the project or absolute, also \\server\share\inbox; subfolders are not searched
patternFile name with wildcards, case-insensitive; default *
intervalTime between checks, default 10s
paramParameter of the target that receives the path
modeeach (default): one run per file · batch: one run with all new files as a JSON list (parameter of type json, e.g. for forEach)
existingprocess (default): process files present at start · ignore
  • The folder is polled – this works on network drives and UNC paths just as locally.
  • A file is ready when it is unchanged across two consecutive checks. So no file is processed while it is still being written.
  • A file counts as processed as soon as its run has started. Moving or deleting it is up to the workflow, e.g. with file.move into an archive.
  • Only the running server knows which files were processed; after a restart, existing applies again.

HTTP (http)

triggers/api.yaml
kind: Trigger
apiVersion: runnel/v1
name: import-api
type: http
target: workflows/nightly-import.workflow.yaml
with:
  method: POST
  path: /hooks/import/{DAY}
  auth: { token: "${secret:env/IMPORT_TOKEN}" }
  response: accepted
  maxConcurrent: 2
FieldMeaning
method, pathGET, POST, PUT, PATCH or DELETE and a path; placeholders {NAME} become parameters
auth{ token: ${secret:…} } or ${env:…} – callers send Authorization: Bearer <token>; auth: none must be stated explicitly
responseaccepted: immediately 202 with the run ID · run: the caller waits for the run's response
timeoutWith run: longest wait for the caller (default 30s), then 504
maxConcurrentRunning runs of this trigger, beyond that 429
historyall, errors or none – which runs are kept
Calling it (PowerShell)
curl.exe -X POST -H "Authorization: Bearer $env:IMPORT_TOKEN" http://127.0.0.1:7301/hooks/import/2026-11-22
  • Parameters come from path, query and body (JSON object or form); for the same name, path beats query beats body. The trigger's fixed params win. If a required parameter is missing or a type doesn't fit: 400, no run.
  • Response from the workflow (response: run): the first http.respond action answers with status, headers and body; without it the outputs are the response (200), a failed run returns 500.
  • Response from a pipeline: the http.response transform answers with the records as JSON. If the target is a pipeline, the body may be a JSON list of objects; it arrives as records via core.from-result.
  • In expressions the request is available as request: request.method, .path, .headers, .query, .body, .client.
  • HTTP triggers run on their own listener, default 127.0.0.1:7301. On the network only with HTTPS – see Operation.
