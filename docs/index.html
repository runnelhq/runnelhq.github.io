Entwicklerdoku

Runnel entwickeln

Runnel ist eine einzige runnel.exe: ein Go-Programm mit eingebettetem Editor in React. Diese Seiten richten sich an alle, die am Kern, am Editor oder an Bausteinen mitarbeiten – Menschen wie KI-Agenten.

Stand: main vom 23.11.2026 · Quelle: AGENTS.md (verbindliche Regeln), CONTRIBUTING.md (Ablauf). Bei Abweichungen gilt das Repository.

Actions entwickeln Schritte für Workflows: Typname, Konfiguration mit Schema-Tags, Execute, Tests. Transforms entwickeln Bausteine für Pipelines: Process, Records, Backpressure, Schema in Init. Editor entwickeln React-Anwendung in web/: Befehle, Aufbau, Regeln, Auslieferung. Server-API Die HTTP-API von runnel serve für Editor und Skripte.
Plugins entwickeln Bausteine in beliebiger Sprache über JSON-RPC. Die Anleitung folgt mit S49–S51.

Schnellstart

Voraussetzungen: Go in der Version aus go.mod (derzeit Go 1.26), golangci-lint v2.15.0 für make lint, Node.js 22 LTS für den Editor und make – unter Windows zum Beispiel über Git Bash. Ohne Node baut make build-go die exe ohne Editor.

Shell
git clone https://github.com/runnelhq/runnel.git
cd runnel
make build                    # bin/runnel mit Editor
make test                     # Tests mit Race-Detector
bin/runnel validate examples
bin/runnel run -v examples/hello/workflows/hello.workflow.yaml
bin/runnel serve examples/hello   # Editor unter http://127.0.0.1:7300

Vor jedem Push müssen make lint und make test grün sein; bei Änderungen am Editor zusätzlich npm run typecheck und die betroffenen Playwright-Tests.

Konventionen

SpracheCode, Kommentare, CLI-Ausgaben, Fehlermeldungen und alle Texte der Oberfläche englisch (ADR 0015); Dokumentation, ADRs, PR-Beschreibungen deutsch.
Typnamen<namensraum>.<name>; Actions und Transforms haben getrennte Namensräume, kein -transform-Suffix (ADR 0013).
MeldungenFehler in Dateien mit Position: datei:zeile:spalte: error|warning: text – für Anwender verständlich, ohne Go-Typnamen.
TestsGolden-Files für Formate und Ausgaben, t.TempDir() statt echter Pfade, plattformunabhängig (Linux und Windows in der CI); geänderte Golden-Dateien im PR-Text begründen.
FuzzingEin neuer Parser für Dateien oder Netzwerkeingaben bekommt im selben PR ein Fuzz…-Ziel in make fuzz.
LeistungFür Pfade mit Last je Datensatz oder Anfrage ein Benchmark (-benchmem) im selben PR, Werte vorher/nachher im PR-Text.
Windows-firstPfade über path/filepath, UNC-Pfade, Kodierungen (BOM, UTF-16) und CRLF berücksichtigen.
Kein VorgriffNur umsetzen, was der aktuelle Roadmap-Schritt verlangt. Nicht Unterstütztes klar melden statt still ignorieren.

Sicherheit

Gilt für alles, was auf Anfragen von außen reagiert – Server, HTTP-Trigger, später Plugins und MCP:

  • Standard nur lokal (127.0.0.1); im Netz nur mit TLS und Authentifizierung. Ausnahmen nur mit ausdrücklichem Schalter und Warnung. Anfragen aus Webseiten (Origin) und DNS-Rebinding abwehren.
  • Grenzen für jede Eingabe: Größe, Zeit und gleichzeitige Läufe.
  • Geheimnisse zeitkonstant vergleichen, nie loggen, nie in Dateien des Projekts.
  • Fehlerantworten ohne interne Details; die Details stehen im Server-Log.
  • Tests für Ablehnungen (401, 403, 413, Timeout) gehören zum PR.

Oberfläche

  • Corporate Design anwenden: Farben, Schriften, Radien und Abstände nur über die Tokens aus design/, keine Hex-Werte im Code.
  • Erst Mockup, dann Umsetzung: Vor jeder neuen oder deutlich geänderten Oberfläche ein Mockup unter design/mockups/ als eigenen PR vorlegen (hell und dunkel, mit Screenshots). Umgesetzt wird erst nach Freigabe.
  • Die Umsetzung folgt dem Mockup; Abweichungen erst im Mockup ändern und erneut freigeben lassen.

Ablauf eines Beitrags

  1. Thema wählen: einen offenen Schritt aus der Roadmap oder ein Issue. Größere Vorhaben vorher in einem Issue abstimmen.
  2. Branch anlegen von main.
  3. Umsetzen nach den Regeln in AGENTS.md: PR-Größe, Tests, Doku, Sicherheit, Mockup vor Oberfläche.
  4. Prüfen: make lint und make test; beim Editor npm run typecheck und Playwright (make e2e); bei Parsern make fuzz, bei Pfaden unter Last make bench.
  5. Pull Request nach main, Titel und Beschreibung deutsch: Zusammenfassung, Änderungen, Entscheidungen fürs Review und „Prüfen“.
  6. CI und Review: Lint (Linux und Windows), Schwachstellen-Check, Tests unter Linux und Windows, Editor (Typprüfung, Playwright), Build und Packen. Gemergt wird bei grüner CI und abgeschlossenem Review.

Pull Requests

  • Genau eine Art je PR: Schritt, Mockup, ADR, Roadmap/Backlog, Fix oder Qualität.
  • Ein Roadmap-Schritt = ein PR, Richtwert höchstens ca. 800 geänderte Zeilen Produktivcode (Go, TS/TSX); Tests, Golden-Dateien, Doku und Beispiele zählen nicht mit. Größere Schritte werden vorher geteilt (S38b1, S38b2 …).
  • Lauffähig nach jedem PR – nichts „halb fertig“ freigeschaltet; jeder Schritt nennt, wie man ihn ausprobiert.
  • Doku im selben PR: Konzept, Roadmap (Schritt mit ✅), ADRs, README, docs/dev/.
  • ADR nötig bei neuem Dateityp, geänderter Ausführungssemantik, neuer Laufzeitabhängigkeit, neuer Netzwerk- oder Sicherheitsgrenze sowie Namens- oder Sprachregeln – vorher mit dem Maintainer abstimmen.
  • Commit-Nachrichten und PR-Titel deutsch im Format <Art oder Schritt>: <Inhalt>, z. B. S38c: … oder Fix: ….
  • Nicht tun: Tests überspringen oder abschwächen, Golden-Dateien ohne Prüfung überschreiben, Secrets in Code, Tests oder Logs, Release- und CI-Workflows ohne Auftrag ändern.

Hinweise für KI-Agenten

AGENTS.md ist die einzige verbindliche Quelle der Regeln – für Coding-Agenten wie Claude Code, Copilot oder Codex ebenso wie für Menschen; CLAUDE.md verweist darauf. Ist das lokale golangci-lint zu alt, hilft go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0 run ./....

Weiterführend

  • Konzept und Architektur
  • Roadmap
  • Testplan und bekannte Einschränkungen
  • Architekturentscheidungen (ADR)
  • Fehler melden – mit runnel version, Windows-Version, Workflow (ohne Secrets) und vollständiger Ausgabe. Sicherheitslücken bitte nicht als Issue, sondern nach SECURITY.md.

Developer docs

Developing Runnel

Runnel is a single runnel.exe: a Go program with an embedded React editor. These pages are for everyone who works on the core, the editor or components – humans and AI agents alike.

As of main on 2026-11-23 · Source (German): AGENTS.md (binding rules), CONTRIBUTING.md (process). If anything differs, the repository is authoritative.

Developing actions Workflow steps: type name, configuration with schema tags, Execute, tests. Developing transforms Pipeline components: Process, records, backpressure, schema in Init. Developing the editor React app in web/: commands, layout, rules, delivery. Server API The HTTP API of runnel serve for the editor and scripts.
Developing plugins Components in any language via JSON-RPC. The guide follows with S49–S51.

Quick start

Prerequisites: Go as specified in go.mod (currently Go 1.26), golangci-lint v2.15.0 for make lint, Node.js 22 LTS for the editor, and make – on Windows e.g. via Git Bash. Without Node, make build-go builds the executable without the editor.

Shell
git clone https://github.com/runnelhq/runnel.git
cd runnel
make build                    # bin/runnel with editor
make test                     # tests with race detector
bin/runnel validate examples
bin/runnel run -v examples/hello/workflows/hello.workflow.yaml
bin/runnel serve examples/hello   # editor at http://127.0.0.1:7300

Conventions

LanguageCode, comments, CLI output, error messages and all UI texts in English (ADR 0015); documentation, ADRs and PR descriptions in German.
Type names<namespace>.<name>; actions and transforms have separate namespaces, no -transform suffix (ADR 0013).
MessagesErrors in files carry a position: file:line:column: error|warning: text – understandable for users, no Go type names.
TestsGolden files for formats and output, t.TempDir() instead of real paths, platform-independent (Linux and Windows in CI); explain changed golden files in the PR text.
FuzzingA new parser for files or network input gets a Fuzz… target in make fuzz in the same PR.
PerformancePaths with load per record or request get a benchmark (-benchmem) in the same PR, with before/after numbers in the PR text.
Windows firstUse path/filepath; handle UNC paths, encodings (BOM, UTF-16) and CRLF.
No anticipationOnly implement what the current roadmap step requires. Report what is unsupported instead of silently ignoring it.

Security

Applies to everything that responds to outside requests – server, HTTP triggers, later plugins and MCP:

  • Local by default (127.0.0.1); on the network only with TLS and authentication. Exceptions only with an explicit switch and a warning. Fend off requests from web pages (Origin) and DNS rebinding.
  • Limits for every input: size, time and concurrent runs.
  • Secrets: compare in constant time, never log them, never put them in project files.
  • Error responses without internal details; the details go to the server log.
  • Tests for rejections (401, 403, 413, timeout) belong in the PR.

User interface

  • Apply the corporate design: colors, fonts, radii and spacing only via the tokens in design/, no hex values in code.
  • Mockup first, then implementation: before any new or substantially changed UI, submit a mockup under design/mockups/ as a separate PR (light and dark, with screenshots). Implementation starts after approval.
  • The implementation follows the mockup; deviations are changed in the mockup first and approved again.

How to contribute

  1. Pick a topic: an open step from the roadmap or an issue. Discuss larger changes in an issue first.
  2. Create a branch from main.
  3. Implement following the rules in AGENTS.md: PR size, tests, docs, security, mockup before UI.
  4. Check: make lint and make test; for the editor npm run typecheck and Playwright (make e2e); for parsers make fuzz, for paths under load make bench.
  5. Pull request to main, title and description in German: summary, changes, decisions for the review and “Prüfen”.
  6. CI and review: lint (Linux and Windows), vulnerability check, tests on Linux and Windows, editor (type check, Playwright), build and packaging. Merged when CI is green and the review is done.

Pull requests

  • Exactly one kind per PR: step, mockup, ADR, roadmap/backlog, fix or quality.
  • One roadmap step = one PR, roughly 800 changed lines of production code (Go, TS/TSX) at most; tests, golden files, docs and examples don't count. Larger steps are split beforehand (S38b1, S38b2 …).
  • Runnable after every PR – nothing “half done” is enabled; every step says how to try it.
  • Docs in the same PR: concept, roadmap (step marked ✅), ADRs, README, docs/dev/.
  • An ADR is needed for a new file type, changed execution semantics, a new runtime dependency, a new network or security boundary, and naming or language rules – agreed with the maintainer first.
  • Commit messages and PR titles in German in the format <kind or step>: <content>, e.g. S38c: … or Fix: ….
  • Don't: skip or weaken tests, overwrite golden files without review, put secrets in code, tests or logs, change release or CI workflows without being asked.

Notes for AI agents

AGENTS.md is the single binding source of the rules – for coding agents such as Claude Code, Copilot or Codex as well as for humans; CLAUDE.md points to it. If the local golangci-lint is too old, use go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0 run ./....
