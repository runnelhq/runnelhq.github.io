Entwicklerdoku · Server

Server-API

Die API von runnel serve ist die einzige Schnittstelle des Editors zum Server – und ebenso für Skripte nutzbar. Außerhalb von /api/v1 liefert der Server den eingebetteten Editor aus.

Quelle: docs/dev/API.md (Stand S38c) – mit allen Feldern und den Endpunkten zum Bearbeiten, Kopieren, Felder ermitteln und zur Datenvorschau. Grundlagen: ADR 0016 (Live-Ereignisse), ADR 0018 (HTTP-Trigger).

Server starten
runnel serve examples/hello     # Projekt im Ordner oder darüber, Port 7300
runnel serve --port 0 .          # freier Port; die Ausgabe nennt die Adresse

Grundsätze

Adressenur 127.0.0.1; HTTP-Trigger haben einen eigenen Listener
Präfixalle Endpunkte unter /api/v1
FormatJSON (UTF-8, eingerückt); Dateiinhalte als Rohdaten
FehlerStatuscode und {"error": "…"} mit englischer, verständlicher Meldung
SchutzAnfragen müssen an localhost, 127.0.0.1 oder [::1] gerichtet sein (Schutz vor DNS-Rebinding); ein Origin-Header muss zum Server passen (Schutz vor fremden Webseiten). Sonst 403
Pfaderelativ zum Projektordner, Trenner /; versteckte Einträge, .., \, : und unter Windows reservierte Namen (CON, NUL …) werden mit 400 abgelehnt

Endpunkte

MethodePfadErgebnis
GET/versionVersion, Commit, Datum, Go-Version, OS, Architektur – wie runnel version --json
GET/projects/currentName, Ordner, Environments und Standard-Environment
GET/projects/current/treeDateibaum mit Art je Datei (workflow, pipeline, project, environment, trigger, document, image, other)
GET · PUT · DELETE/files/{path}Datei lesen (mit ETag), speichern (max. 10 MiB) oder löschen – mit Konfliktschutz
POST · DELETE/foldersOrdner anlegen bzw. leeren Ordner löschen
POST/renameDatei oder Ordner umbenennen oder verschieben, Verweise auf Wunsch mit ändern
GET/references/{path}Stellen, die auf eine Datei verweisen (Trigger-Ziele, Aufrufe mit festem Pfad)
GET/variablesVariablen des Projekts mit Werten je Ebene und Fundstellen
GET/schemas/{kind}JSON Schema einer Dateiart (project, environment, trigger) – wie runnel schema
GET/catalogDescriptors aller Actions und Transforms – wie runnel catalog --json
GET/expressionsReferenz für den Ausdruckseditor: Kontext, Funktionen, Variablen
POST/validateWorkflow, Pipeline oder Projektdatei prüfen – gespeichert oder mit ungespeichertem content, genau wie runnel validate
POST/workflows/edit, /pipelines/editÄnderung vom Canvas zeilengenau auf den Text anwenden (nicht speichern)

GET/triggersTrigger des Projekts mit Zeitplan, nächstem Zeitpunkt und letztem Ergebnis

Konfliktschutz (ETag)

Jede Datei hat ein ETag (Hash des Inhalts). Gespeichert wird nur, wenn sich die Datei seit dem Laden nicht geändert hat – egal ob durch einen anderen Browser, einen Texteditor oder git pull.

AnfrageDatei existiertDatei fehlt
PUT ohne If-Match428 – ETag erforderlich201 – angelegt
PUT mit passendem If-Match200 – ersetzt–
PUT mit anderem If-Match412 – „changed in the meantime“412 – „deleted in the meantime“
DELETE ohne / mit passendem / mit anderem If-Match428 / 204 / 412428 / 412 / 412

If-Match: * überschreibt bewusst ohne Prüfung. Gespeichert wird atomar: temporäre Datei, dann Umbenennen.

Läufe

Lauf starten und verfolgen
# Lauf starten (Environment und Parameter sind optional)
curl -X POST http://127.0.0.1:7300/api/v1/runs \
  -H "Content-Type: application/json" \
  -d '{"path": "workflows/hello.workflow.yaml", "environment": "prod", "params": {"GREETING": "Moin"}}'

# Ereignisse live verfolgen (Server-Sent Events)
curl -N "http://127.0.0.1:7300/api/v1/events?run=<id>"

Gestartet wird die gespeicherte Datei – Workflow oder Pipeline –, vorher wird sie wie bei runnel run geprüft.

AntwortBedeutung
201 + Run, Header LocationLauf gestartet; er läuft im Hintergrund weiter
422Fehler in Workflow oder Projektdateien (Format wie /validate)
400unbekanntes Environment, Parameter fehlen oder passen nicht zum Typ
429Limit gleichzeitiger Läufe erreicht (settings.maxConcurrentRuns)
404 / 503Datei nicht gefunden / Server wird beendet
Run
{
  "id": "01M7T2X0AHHW9G9ZAV04RRCXJC",
  "path": "workflows/parallel.workflow.yaml",
  "kind": "workflow",
  "workflow": "parallel",
  "trigger": "cron:nightly",
  "client": "127.0.0.1",
  "environment": "dev",
  "status": "running",
  "started": "2026-11-19T14:20:50.898Z",
  "finished": "2026-11-19T14:20:52.899Z",
  "durationMs": 2001,
  "error": "…",
  "outputs": { "MESSAGE": "Hello" }
}

status ist running, succeeded, failed oder cancelled; trigger nennt, was den Lauf gestartet hat (cron:<name>, interval:…, file:…, http:…). GET /runs/{id} ergänzt den Status je Action und das Log (höchstens 5.000 Zeilen). Läufe liegen nur im Speicher – die letzten 100, dazu die letzten 100 von HTTP-Triggern; eine dauerhafte Historie folgt mit S26, ohne dass sich die API ändert.

Live-Ereignisse (/events)

Beispiel
id: 7
event: log
data: {"seq":7,"kind":"log","time":"…","runId":"01M7…","actionId":"fetch-a","actionType":"core.wait","level":"debug","message":"waiting 2s"}
EreignisZusätzliche Felder
run.startedmessage (Name)
action.startedactionId, actionType
logactionId, level, message
action.finishedstatus, durationMs, error; bei Transforms counts und linkRows
action.skipped, action.waitingstatus, bei waiting eine message
run.finishedstatus, durationMs, error, outputs
resetverpasste Ereignisse sind nicht mehr vorrätig; Zustand über GET /runs neu laden
  • Ohne Angabe kommen nur neue Ereignisse. Mit Last-Event-ID oder ?since=<seq> folgen zuerst die verpassten; vorrätig sind die letzten 2.000.
  • ?run=<id> liefert nur die Ereignisse eines Laufs. Alle 15 s hält ein Kommentar (: ping) die Verbindung offen.

HTTP-Trigger

HTTP-Trigger antworten nicht unter /api/v1, sondern auf einem eigenen Listener (--triggers, Standard 127.0.0.1:7301; im Netz per HTTPS) unter den Pfaden ihrer Trigger-Dateien.

AntwortBedeutung
202 + {"runId", "status"}response: accepted: Lauf gestartet
Antwort von http.respondresponse: run: die erste Antwort des Laufs; ohne http.respond 200 mit den outputs bzw. 500
504response: run: keine Antwort innerhalb von timeout; der Lauf läuft weiter
400 / 401 / 403Parameter fehlt oder passt nicht / Token fehlt oder falsch / Anfrage aus einer Webseite
404 / 405kein Trigger für den Pfad / andere Methode
413 / 415 / 429Body über 1 MiB / weder JSON noch Formular / Limit gleichzeitiger Läufe

Developer docs · Server

Server API

The API of runnel serve is the editor's only interface to the server – and just as usable from scripts. Outside /api/v1 the server delivers the embedded editor.

Source (German): docs/dev/API.md (as of S38c) – with every field and the endpoints for editing, copying, field detection and data preview. Background: ADR 0016 (live events), ADR 0018 (HTTP triggers).

Start the server
runnel serve examples/hello     # project in the folder or above, port 7300
runnel serve --port 0 .          # free port; the output names the address

Principles

Address127.0.0.1 only; HTTP triggers have their own listener
Prefixall endpoints under /api/v1
FormatJSON (UTF-8, indented); file contents as raw data
ErrorsStatus code and {"error": "…"} with an understandable English message
ProtectionRequests must target localhost, 127.0.0.1 or [::1] (DNS rebinding protection); an Origin header must match the server (protection against other web pages). Otherwise 403
Pathsrelative to the project folder, separator /; hidden entries, .., \, : and names reserved on Windows (CON, NUL …) are rejected with 400

Endpoints

MethodPathResult
GET/versionVersion, commit, date, Go version, OS, architecture – like runnel version --json
GET/projects/currentName, folder, environments and default environment
GET/projects/current/treeFile tree with a kind per file (workflow, pipeline, project, environment, trigger, document, image, other)
GET · PUT · DELETE/files/{path}Read a file (with ETag), save it (max. 10 MiB) or delete it – with conflict protection
POST · DELETE/foldersCreate a folder or delete an empty one
POST/renameRename or move a file or folder, optionally updating references
GET/references/{path}Places that refer to a file (trigger targets, calls with a fixed path)
GET/variablesProject variables with values per level and usages
GET/schemas/{kind}JSON Schema of a file kind (project, environment, trigger) – like runnel schema
GET/catalogDescriptors of all actions and transforms – like runnel catalog --json
GET/expressionsReference for the expression editor: context, functions, variables
POST/validateCheck a workflow, pipeline or project file – saved or with unsaved content, exactly like runnel validate
POST/workflows/edit, /pipelines/editApply a canvas change to the text line by line (without saving)
POST/copyActions or transforms as YAML text for the clipboard
POST/pipelines/fieldsDetect the fields of an input transform
POST/previewData preview of a pipeline up to a transform
POST · GET/runs, /runs/{id}Start a run; list runs or read one with status per action and log
POST/runs/{id}/cancelCancel a run (202; already finished 409)
GET/eventsLive events as server-sent events
GET/triggersProject triggers with schedule, next time and last result

Conflict protection (ETag)

Every file has an ETag (hash of its content). A save only succeeds if the file hasn't changed since it was loaded – whether by another browser, a text editor or git pull.

RequestFile existsFile missing
PUT without If-Match428 – ETag required201 – created
PUT with matching If-Match200 – replaced–
PUT with other If-Match412 – “changed in the meantime”412 – “deleted in the meantime”
DELETE without / matching / other If-Match428 / 204 / 412428 / 412 / 412

If-Match: * deliberately overwrites without a check. Saving is atomic: temporary file, then rename.

Runs

Start and follow a run
# start a run (environment and parameters are optional)
curl -X POST http://127.0.0.1:7300/api/v1/runs \
  -H "Content-Type: application/json" \
  -d '{"path": "workflows/hello.workflow.yaml", "environment": "prod", "params": {"GREETING": "Moin"}}'

# follow events live (server-sent events)
curl -N "http://127.0.0.1:7300/api/v1/events?run=<id>"

The saved file is started – workflow or pipeline – after the same checks as runnel run.

ResponseMeaning
201 + run, header LocationRun started; it keeps running in the background
422Errors in the workflow or project files (format as /validate)
400Unknown environment, parameters missing or of the wrong type
429Limit of concurrent runs reached (settings.maxConcurrentRuns)
404 / 503File not found / server shutting down
Run

  "id": "01M7T2X0AHHW9G9ZAV04RRCXJC",
  "path": "workflows/parallel.workflow.yaml",
  "kind": "workflow",
  "workflow": "parallel",

  "client": "127.0.0.1",
  "environment": "dev",
  "status": "running",
  "started": "2026-11-19T14:20:50.898Z",
  "finished": "2026-11-19T14:20:52.899Z",
  "durationMs": 2001,
  "error": "…",
  "outputs": { "MESSAGE": "Hello" }

status is running, succeeded, failed or cancelled; trigger names what started the run (cron:<name>, interval:…, file:…, http:…). GET /runs/{id} adds the status per action and the log (at most 5,000 lines). Runs are kept in memory only – the last 100 plus the last 100 from HTTP triggers; a persistent history follows with S26 without changing the API.

Live events (/events)

Example
id: 7
event: log
data: {"seq":7,"kind":"log","time":"…","runId":"01M7…","actionId":"fetch-a","actionType":"core.wait","level":"debug","message":"waiting 2s"}
EventAdditional fields
run.startedmessage (name)
action.startedactionId, actionType
logactionId, level, message
action.finishedstatus, durationMs, error; for transforms counts and linkRows
action.skipped, action.waitingstatus, for waiting a message
run.finishedstatus, durationMs, error, outputs
resetMissed events are no longer available; reload the state via GET /runs
  • Without parameters only new events arrive. With Last-Event-ID or ?since=<seq> the missed ones come first; the last 2,000 are kept.
  • ?run=<id> delivers only the events of one run. A comment (: ping) every 15 s keeps the connection open.

HTTP triggers

HTTP triggers do not answer under /api/v1 but on their own listener (--triggers, default 127.0.0.1:7301; HTTPS on the network) at the paths of their trigger files.

ResponseMeaning
202 + {"runId", "status"}response: accepted: run started
Response of http.respondresponse: run: the run's first response; without http.respond 200 with the outputs or 500
504response: run: no response within timeout; the run keeps going
400 / 401 / 403Parameter missing or invalid / token missing or wrong / request from a web page
404 / 405No trigger for the path / other method
413 / 415 / 429Body over 1 MiB / neither JSON nor form / concurrent run limit
